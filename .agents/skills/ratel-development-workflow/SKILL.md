# Ratel 开发工作流

编码任务先分档再选择流程；纯文档重组、Skill 安装与规则维护按实际检查，不为此自动启动产品 spec 或完整编码 SDD。用户明确指定的范围和流程优先。

## 任务分档

> 前置门槛:接到编码任务后、动手前,先按下表判定档位并告诉用户「本任务按 X 档执行」。禁止对所有任务默认拉满完整 SDD(成本与改动量不匹配时就是浪费)。

| 档 | 触发条件(满足全部) | 执行方式(必须遵守) |
|---|---|---|
| **小档** | ① 单文件或 ≤2 文件;② 净改动 ≤ ~40 行;③ 无数据模型/跨线程/权限/持久化迁移;④ 无新的异步并发或状态机 | 主代理直接改 + 定向测试自验。**不派实现 subagent、不做两阶段审查、不写 plan 文件**;brainstorming/spec 也跳过(口头一句话说明即可)。仍须 TDD(有逻辑可测时)、i18n、注释、隐私规范 |
| **中档** | 1-3 文件、含 UI 交互/异步状态/非平凡纯逻辑,但不碰架构契约 | 1 个实现 subagent;审查由主代理自己完成(对照需求读 diff + 跑验证),不再派独立审查 subagent;有 spec/plan 简短登记即可 |
| **大档** | 满足任一:跨子系统、数据模型或接口契约变更、并发/持久化迁移、单任务净改动 > ~150 行、用户明确要求完整流程 | 完整 subagent-driven-development:逐任务新 subagent + 两阶段独立审查;spec/plan 齐全 |

规则:

1. **档位先于技能动作判定** — 判为小档时,即使触发了 brainstorming/SDD 技能,也按本节降档执行(本节是本仓库对技能的显式收窄,符合「用户指令优先于技能」)。
2. **拿不准就高一档** — 边界模糊时按高一档执行,并在回复中说明为什么。
3. **用户可随时改档** — 用户说「直接改」=强制小档;说「认真审」=强制大档,无须再劝。
4. **同分支多个独立小改可合并执行**,但提交仍按逻辑分组(见既有提交偏好:少量几个、不碎成一堆)。
5. **停止条件** — 小档执行中发现实际改动超过触发条件(冒出第二个文件外的牵连、需要动契约),立即停止扩写,向用户说明并升档,不得默默把小档做成大档。

## 工程流程

- 小档按上述例外直接实施；中档保留简短设计/计划登记；大档按 brainstorming → writing-plans → TDD → subagent-driven-development → 审查 → 实际验证执行。
- 调试使用 systematic-debugging，先定位证据与根因；完成前使用 verification-before-completion，不把未执行的检查写成通过。
- 编码和审查加载 [编码约定](../ratel-code-conventions/SKILL.md)；spec/plan 建立、执行与归档调用 [项目管理](../ratel-project-management/SKILL.md) 同步登记和 Project。
- 这些 Superpowers 技能使用宿主实际提供的安装源；先检查可用技能。仓库 `.superpowers/` 是被忽略的本地工作区，不把它硬编码成技能源；必要技能缺失时说明，不能虚构已调用。
- 采用 SDD 时每个实现任务使用新 subagent，并先审规范再审代码质量；中、小档按分档例外，不机械套用全套。Critical 问题阻塞完成，验证范围以变更风险和用户要求为准。

## 收尾与文档

每次开发收尾读取 [文档影响检查](references/document-sync.md)，即使没有调用 finishing-a-development-branch 也不能漏掉。已明确授权的文档范围直接补齐，不重复请求同一授权；未授权的架构变更按参考规则确认。

用户要求发版时由 `releasing-obsidian-plugin` 接管发布准备、文档确认和 git 硬闸，不重复执行两套确认。未获“发”的指令前不得绕过发布 Skill 的限制。
