## 1. 背景

Ratel 0.5.0 已具备融合检索、可点击引用、多步工具、分层记忆、Skill（含沙箱脚本执行）、MCP、Subagent、模型可替换、对话式配置、权限分级与本地嵌入。它已经越过“和 Vault 聊天”的基础门槛，但现有对外叙事仍以功能清单为主：图谱、检索、扩展、模型与隐私并列出现，用户难以快速理解 Ratel 为什么值得长期使用。

当前市场中，语义找回、Vault 问答、Agent 工具、图谱感知、本地模型、Skill 与 MCP 已分别被多个 Obsidian AI 产品覆盖。继续以“功能更多”竞争，会进入同质化与功能军备竞赛。Ratel 需要把已有能力组织成一个更清楚的产品人格。

与此同时，Obsidian 的能力生态已成长到 2000+ 社区插件，「发现该装什么、装完怎么配、坏了怎么恢复」成为各类用户的持续摩擦：新手面对商店无从下手，重度用户的插件组合维护成本随规模上升。Ratel 作为生长在 Obsidian 内的 Agent，理解自然语言需求，天然适合接管这层环境管理——从「回答问题的 Agent」升级为「能动手搭环境的 Agent」。这是当前 Obsidian AI 竞品均未覆盖的差异化空档。

本 PRD 来自作者自身的真实使用场景。目标用户同时是：

- A 类：拥有千级以上双链笔记，长期使用日记、项目笔记与链接结构的知识工作者；
- C 类：重视模型自由、Skill、MCP 与 Subagent，可自行定义 Agent 工作方式的高级用户。

用户确认的核心判断如下：

- “找回旧笔记”非常重要，但现有能力对千级笔记已基本够用；
- 知识挖掘重要且有差异化，但不是每天必须发生的刚需；
- 单纯生成笔记无法形成竞争力，必须嵌入复盘、建议、治理或研究闭环；
- 主动智能与知识熵管理更可能形成独特价值；
- 插件生态的探索、安装与配置是 Obsidian 用户的普遍痛点，适合 Agent 代劳；但环境变更属敏感操作，必须以路径白名单物理校验、事前备份与可回滚为前提；
- 第一阶段先在 Obsidian 内完成 Heartbeat、洞察收件箱与系统通知闭环；外部消息通道后置评估。

## 2. 产品定位

### 2.1 核心定位

**Ratel 是主动智能的 Obsidian 知识与环境管理 Agent。**

它让知识库和工作环境主动参与每天的工作。知识侧：在用户授权的范围内理解记忆约定与日记上下文，复盘昨天、建议今天、发现知识熵、挖掘跨笔记关系；环境侧：通过对话完成插件生态的发现、安装、配置与维护，每次变更先备份、留日志、可回滚。两者都通过 Obsidian 内的洞察与通知持续协作。

### 2.2 产品能力栈

| 层级 | 内容 | 用户价值 |
|---|---|---|
| 品牌承诺 | 主动智能 × 知识与环境管理 | 知识库和工作环境不再只等用户搜索与手动折腾，而会在合适时间主动参与工作 |
| 产品支柱 A | Heartbeat、记忆感知、主动简报、建议、洞察收件箱 | 少遗漏、少重复思考、及时获得下一步提示 |
| 产品支柱 B | 融合检索、图谱理解、引用、知识熵治理、知识挖掘 | 找回、理解、维护并产生新知识 |
| 产品支柱 C | 插件商店探索、安装/更新/卸载、其他插件配置、变更日志与回滚 | 用自然语言搭好工具环境，敏感变更有据可查、可撤销 |
| 开放 Agent 底座 | 模型自由、Skill、MCP、Subagent | 产品能适应不同工作流，而不是把用户锁进单一模型或流程 |
| 信任护栏 | 本地优先、黑名单、最小披露、权限、确认、审计、备份与回滚 | 主动但不越界，提醒但不擅自行动，改了就能查、能撤 |

### 2.3 Messaging Framework

- **使命:** 让长期积累的个人知识与工作环境在保持所有权与控制权的前提下，主动帮助用户完成每天的思考与行动。
- **价值主张:** 对于认真经营 Obsidian 双链库、又希望掌控 Agent 工作流的知识工作者，Ratel 是一个主动智能的知识与环境管理 Agent。不同于只回答问题的 Vault Chat，Ratel 会基于记忆、日记与知识图，在合适时间带着证据复盘、提醒、治理并协助行动；也能通过对话完成插件生态的发现、安装与配置，每次变更可追溯、可回滚。
- **主要信息:** 让你的 Obsidian 主动工作——知识与环境都交给 Agent。
- **可信理由:** 本地嵌入、融合检索、可点击引用、黑名单、独立工具权限、普通 Markdown 记忆、开放模型、Skill、MCP 与 Subagent；生态变更有白名单校验、备份与一键回滚。

## 3. 目标与成功定义

### 3.1 产品目标

1. 建立可复用的本地主动智能闭环：观察 → 判断 → 生成洞察 → Obsidian 投递 → 用户反馈 → 记忆更新。
2. 把融合检索、双链结构、引用、知识熵治理与知识挖掘统一为图知识管理能力。
3. 通过 Obsidian Notice、状态栏和洞察收件箱完成分级、可处理的本地通知体验。
4. 让模型自由、Skill、MCP 与 Subagent 成为产品底座，而不是 README 首屏的并列功能清单。
5. 在任何主动场景中保持黑名单、最小披露、权限确认与可审计性。
6. 让用户通过对话完成插件生态的发现、安装、配置、更新与卸载；所有环境变更留有 append-only 日志与可恢复备份。

### 3.2 用户成功

- 用户每天无需主动打开聊天，也能收到一次不重复、有证据、可处理的有效洞察。
- 用户在 Obsidian 内能从系统提醒进入洞察详情，完成查看来源、追问、忽略、稍后或确认写入。
- 用户能明确知道 Ratel 为什么提醒、读了哪些来源、调用了什么外部能力、是否修改了 Vault。
- 用户说“没有月度任务位置”后，Ratel 会记住这个缺失约定，不再反复追问，直到用户主动更新。
- 用户无需重新维护一套任务数据库即可使用主动智能。
- 用户说“我想要一个看板”，Ratel 推荐社区插件并说明理由；确认后安装、启用、即装即用，无需重启。
- 用户随时能查看“Ratel 对我的环境做过什么”的完整变更历史，并可一键回滚任意一次变更。

## 4. 非目标

- 不把 Ratel 做成独立任务管理器，不要求用户迁移到新的 task schema。
- 不要求用户先整理好链接、标签或文件夹才能获得基础价值。
- 不把整个 Vault 默认发送给远程模型或 MCP Server。
- 不允许 Heartbeat 自动修改用户笔记；所有写入仍需用户明确接受。
- 当前阶段不实现外部消息通道；本地主动闭环稳定后再独立立项。
- 不以“支持最多模型、工具或协议”作为首要市场叙事。
- 不做插件商店浏览 UI：生态管理的入口是对话，不复制 Obsidian 原生商店界面。
- 不代改 Obsidian 核心配置（外观、快捷键、核心插件等官方设置）：只引导定位到对应设置页。
- 不安装社区商店清单之外的来源（裸 URL、本地旁路包）：防恶意分发。
- 不做主题与 CSS snippet 管理（后续独立评估）。
- 不承诺 Obsidian 关闭后仍能计算或投递新洞察；运行边界见第 10 节。

## 5. 用户、场景与核心实体

### 5.1 目标用户

首要用户是作者本人及相似用户：研究者、写作者、产品与技术人员。他们拥有长期积累的 Markdown Vault，使用双链、日记与项目笔记，同时愿意配置模型、Skill 或 MCP 来形成个人工作流。

### 5.2 核心 Job to be Done

| 场景 | 用户要完成的工作 | Ratel 的角色 |
|---|---|---|
| 每日开始 | 理解昨天发生了什么、今天最该做什么 | 基于记忆约定与日记证据生成简报和建议 |
| 模糊找回 | 找到记过但忘了位置的想法 | 融合检索、图关系与可点击引用 |
| 知识维护 | 发现断链、重复、过时与遗漏 | 本地检测候选，生成可解释治理洞察 |
| 知识挖掘 | 从分散笔记发现主题、关系、缺口与矛盾 | 组合检索、图谱、Skill、MCP 与 Subagent 深挖 |
| 主动提醒 | 不打开聊天也能发现值得处理的信息 | Obsidian 系统通知、状态栏与洞察收件箱 |
| 搭建环境 | 找到并配好需要的插件工具 | 理解需求 → 商店推荐 → 确认后安装 → 配置生效，变更可回滚 |

### 5.3 产品实体

| 实体 | 含义 | 关键状态 |
|---|---|---|
| `RoutineContract` | 从记忆中解析出的工作约定，如日记位置与月度目标位置 | active / absent / superseded |
| `HeartbeatRule` | 定义触发条件、冷却时间、优先级与所需约定 | enabled / due / cooling / blocked |
| `Insight` | 主动生成、等待用户处理的洞察 | pending / delivered / accepted / snoozed / ignored / expired |
| `EvidenceRef` | 支撑回答或洞察的笔记、片段、图关系与检索来源 | local-only / model-shared / mcp-shared |
| `Delivery` | 一次洞察在 Obsidian 内的投递记录 | queued / shown / opened / failed |
| `AuditEvent` | 读取、外发、工具、确认与写入的审计事件 | immutable append-only record |
| `EcosystemChange` | 一次环境变更记录：动作、目标插件、前后摘要、备份位置、回滚状态 | recorded / restored / expired |

## 6. 产品原则

1. **主动，不打扰:** Heartbeat 负责筛选时机和价值，不负责制造通知数量。
2. **先本地筛选，再最小披露:** 本地规则先找候选，模型与 MCP 只接收当前任务需要的证据。
3. **记忆是工作契约:** 用户用自然语言告诉 Ratel 工作约定，不再要求维护第二套配置数据库。
4. **问一次，也记住“没有”:** 缺失位置只询问一次；否定回答形成负向记忆。
5. **证据优先:** 回答、提醒、治理与挖掘结果都必须能回到来源。
6. **通知不是执行:** 系统提醒只负责触达和导航，不能成为绕过工具权限的写入入口。
7. **写入由用户决定:** 洞察可以自动产生，Vault 变更不能自动发生。
8. **环境变更可逆:** 对 Obsidian 环境的任何修改（安装、更新、卸载、插件配置、启用清单）必须先备份、留日志、可回滚；Agent 不确定时不修改。
9. **底座开放，产品聚焦:** 模型、Skill、MCP 与 Subagent 保持开放，但服务于主动智能、知识与环境管理。

## 7. 详细功能设计

### 7.1 主动智能

**Heartbeat**

Heartbeat 是主动场景的调度底座，不直接等价于通知。它必须：

- 仅在到期、有新证据且不处于冷却期时启动规则；
- 按本地日期去重，同一规则同一周期最多生成一个有效洞察；
- 支持优先级、安静时段、冷却时间、失败退避与手动刷新；
- 先运行本地低成本判断，再决定是否调用模型；
- 记录触发原因、跳过原因与最终投递状态；
- 不在索引未就绪、模型不可用或关键约定缺失时反复重试打扰用户。

**记忆约定解析**

Ratel 从现有记忆系统读取日记、月度目标、项目位置与偏好。解析结果形成 `RoutineContract`，但事实源仍是普通 Markdown 记忆。

- 找到明确位置：验证存在后使用；位置变化时由用户主动更新。
- 未找到约定：创建一条低优先级澄清问题进入洞察收件箱。
- 用户回答“没有”：记录 `absent`，后续不再询问。
- 用户主动提供新位置：新约定取代旧的 active/absent 记录。
- 约定冲突：展示冲突来源，不静默猜测。

**昨日简报与今日建议**

- 每天首次满足条件时，先生成昨日简报；依据昨日记忆、日记、近期修改和相关项目证据。
- 若月度目标与今日日记均可定位，再生成今日建议；缺少任一项时只做可完成部分。
- 简报与建议是两个可独立审阅的区块，共享一组来源与触发说明。
- 不为填满版面编造建议；证据不足时明确写“没有足够证据”。

**洞察收件箱**

所有主动结果先进入统一洞察收件箱。每条洞察提供：

- 标题、摘要、优先级、生成时间与过期时间；
- 触发原因与使用来源；
- 是否调用远程模型或 MCP，以及对应披露范围；
- `写入今日日记`、`稍后`、`忽略`、`继续追问` 操作；
- 接受/忽略原因的可选反馈。

Heartbeat 不直接写日记。用户接受后才通过现有工具权限与 Write Gate 写入，并返回可打开的目标链接。

**通知策略**

通知策略根据优先级和用户状态决定投递：

- 状态栏显示未处理洞察数量，始终提供稳定入口；
- 高价值且时效明确的洞察使用 Obsidian Notice 展示短摘要；
- 点击 Notice 打开对应洞察详情，而不是把完整内容塞进系统通知；
- 低价值洞察只入收件箱，不主动弹出；
- 支持安静时段、每日上限与按规则关闭。

### 7.2 图知识管理

**融合检索与图谱理解**

- 语义与关键词保证未整理 Vault 的召回下限；
- 双链、反链、标签与属性提供结构增益；
- 图扩邻必须识别 Daily/MOC 等高扇出 hub，避免噪声扩散；
- 所有回答与研究结果保留可点击引用；
- 洞察和对话中的来源均以稳定编号呈现，并可在 Obsidian 中一键打开。

**知识熵治理**

治理能力先在本地生成候选，再由 Agent 判断是否值得形成洞察。候选包括：

- 未解析链接与断链；
- 孤儿笔记与长期未被引用的内容；
- 高相似重复笔记或重复段落；
- 与当前约定冲突或疑似过时的内容；
- 长期未完成且仍关联当前目标的任务；
- 结构异常，如同类笔记属性不一致。

每条治理建议必须说明检测信号、相关来源、置信度和建议动作。修改、合并、补链、归档或删除必须经过用户确认。

**知识挖掘**

知识挖掘是图知识管理的高价值差异化能力，不局限于搜索结果摘要：

- 聚合跨笔记主题、概念与关系；
- 发现未显式连接但证据一致的潜在关系；
- 标记知识缺口、冲突观点与需要更新的结论；
- 生成带来源的专题综述、关系说明与阅读队列；
- 允许 Skill 定义研究方法、MCP 补充外部资料、Subagent 分工检索/审查/写作；
- 产出先进入对话或洞察收件箱，用户确认后再沉淀为笔记。

### 7.3 生态管理

Ratel 的管理对象从知识库扩展到工作环境。按归属分三域，能力与边界各不相同：

| 域 | 对象 | Agent 能力 |
|---|---|---|
| Ratel 自身 | 本插件设置、密钥、技能 | 读配置、白名单内代改、密钥只看状态、定位设置页（已有能力） |
| Obsidian 官方 | 核心设置（外观、快捷键、核心插件） | 只引导：定位到对应设置页并文字指路，不代改 |
| 社区生态 | 社区插件的安装、配置、更新、卸载 | 全托管：发现、推荐、安装、配置、更新、回滚 |

**商店探索**

- 用户用自然语言描述需求，Agent 在社区插件清单内检索并推荐；
- 推荐结果带作者、下载量、功能说明与「是否已安装」标注，按相关性与热度排序；
- 清单本地缓存并按期刷新；Agent 只把筛选后的候选给模型，不把整份清单塞进上下文。

**安装 / 更新 / 卸载**

- 每次操作先弹确认，弹窗展示动作、目标插件、作者与下载量，决定权在用户；
- 安装与更新从插件官方 GitHub release 拉取产物，写入 `.obsidian/plugins/<id>/`；
- 安装后经运行时 API 启用，即装即用，无需重启 Obsidian；
- 更新只覆盖插件本体（main.js / manifest.json / styles.css），保留其 data.json 用户配置；
- 卸载先备份再移除。

**插件配置**

- Agent 读取目标插件 data.json，向用户解释配置结构；
- 修改以「点名 key + 前后值对比」的最小 diff 进行，不整文件重写；
- 未知结构先展示给用户确认，不猜测写入。

**变更日志与回滚**

- 每次环境变更（含启用清单 community-plugins.json 的每次写入）追加一条 `EcosystemChange`：动作、目标、前后摘要、时间、备份位置；
- 日志 append-only，存本地插件目录，用户可随时查看完整历史；
- 任意一次变更可从对应备份恢复，「撤销刚才的改动」是一等公民能力。

**安全边界**

- 路径白名单在 adapter 层物理校验：仅 `.obsidian/plugins/<清单校验过的 id>/` 与 `community-plugins.json` 可写；Ratel 自身插件目录、Obsidian 核心配置与其余一切路径不可达；
- 只安装商店清单内插件；确认弹窗展示作者与下载量，最终决定权在用户；
- 网络出站扩展（GitHub 清单与 release）需独立 ADR 评审，README 隐私说明同步更新。

### 7.4 本地 Obsidian 通知

本地通知不是独立数据源，而是洞察收件箱的触达层。第一阶段只依赖 Obsidian 提供的能力，先把主动闭环做完整。

**投递层级**

- 状态栏：显示未处理洞察数量，点击打开洞察收件箱；
- 洞察收件箱：承载完整内容、来源、触发原因和所有处理动作；
- Obsidian Notice：只用于高价值、时效明确的洞察，展示标题与短摘要；
- 对话入口：从洞察继续追问时，带上洞察和来源上下文进入正常 Agent 会话。

**通知行为**

- 同一洞察只弹出一次 Notice，插件重载后不重复轰炸；
- Notice 点击后定位到对应洞察，关闭 Notice 不等于忽略洞察；
- 安静时段内只累计未读数，不弹出 Notice；
- 洞察过期后不再弹出，但可按保留策略在收件箱查看；
- 通知失败不影响洞察持久化，用户仍能从状态栏进入处理。

**迭代原则**

先完成昨日简报、条件式今日建议、洞察收件箱、分级通知、用户反馈和受控写入的主要闭环。闭环可持续使用后，再根据真实反馈优化规则、排序、摘要和通知节奏；外部消息通道另行立项。

### 7.5 开放 Agent 底座

- **模型自由:** 对话、嵌入和重排模型可替换；本地 Ollama 时证据不出本机。
- **Skill:** 定义复盘、治理和挖掘方法，不绕过权限或数据边界。
- **MCP:** 提供网页搜索等外部能力；每个 Server 与工具保留独立权限、出站说明和审计。
- **Subagent:** 复杂挖掘可分派研究、审查与整理角色；子代理继承当前会话的数据范围和权限上限。
- **统一能力池:** 模型按场景选择能力，系统按类型路由，所有执行回到同一权限与事件链路。

### 7.6 自我改进

自我改进让 Ratel 从被纠正中变好，而不是从成功中自我强化。它不引入新存储、不建独立知识库，全部复用现有件：**教训归宿是记忆系统，审阅容器是洞察收件箱，注入走分层**。

**失败信号与教训沉淀**

笔记 Agent 的失败大多发生在用户偏好上：「不要把周记写进 inbox」「我的月度目标在那篇不在这篇」。这些教训只能从被纠正的会话中学到：

- 信号来源：用户显式纠错、对同一问题重问、撤销 AI 的编辑、忽略建议、否定回答（"没有"）；
- 提炼：从失败会话提取一条候选教训（反模式 / 检查项 / 偏好约定），标注来源会话；
- 审阅：候选进入洞察收件箱，用户接受、编辑后接受或拒绝——验证靠用户审阅，不靠统计（个人库流量撑不起统计置信度）；
- 归宿：接受后写入现有记忆系统（普通 Markdown），可读、可编辑、可删除；不新建第二套知识存储。

**分层注入**

- 核心约定（日记位置、月度目标等工作契约）标记为恒注入，不参与检索排序，永不被噪声挤掉；
- 其余记忆与 Skill 按当前查询做相关性检索，只取 top-K 注入——安装 20 个 Skill 不等于 20 份全文进入上下文；
- 注入总量有预算上限，超出时优先保留核心约定与高相关性条目。

**使用反馈**

- Skill 与教训记录被注入、被使用次数，在管理面板可见；
- 不做自动退役：低效条目由用户参考统计自行处置。

**非目标**

- 不做统计 A/B 验证、eval 数据集、效果率自动退役——那是开发者调 Agent 的框架属性；
- 不做 trace 归因 CLI 与知识冲突检测引擎——约定冲突处理沿用 7.1 的「展示来源，不静默猜测」。

## 8. 关键用户流程

### 8.1 每日主动闭环

1. Heartbeat 发现当天尚未生成每日洞察。
2. 本地检查索引、记忆约定和必要位置。
3. 缺失约定则创建一次性澄清；存在约定则构建最小证据包。
4. 模型生成昨日简报；条件满足时附今日建议。
5. 洞察进入收件箱，并按优先级更新状态栏或弹出 Obsidian Notice。
6. 用户接受、稍后、忽略或追问。
7. 接受后才写入今日日记；反馈更新洞察状态与偏好。

### 8.2 本地通知处理

1. 高价值洞察生成后进入收件箱并触发一次 Obsidian Notice。
2. 用户点击 Notice，Ratel 打开对应洞察详情。
3. 用户查看触发原因、来源和外发信息。
4. 用户选择忽略、稍后、继续追问或接受建议。
5. 接受写入时仍进入现有 Write Gate；完成后展示目标笔记链接。

### 8.3 知识熵治理

1. 本地检测器发现候选信号。
2. Heartbeat 根据置信度、近期变化与用户反馈筛选。
3. Agent 生成带证据、非破坏性的治理建议。
4. 建议进入收件箱；用户选择忽略、稍后或执行。
5. 执行仍走工具权限和 Write Gate。

### 8.4 知识挖掘

1. 用户从 Obsidian 提出研究问题，或接受主动挖掘建议。
2. Agent 组合融合检索与图谱邻域，必要时激活 Skill、MCP 与 Subagent。
3. Reviewer 检查来源覆盖、冲突与过度推断。
4. 输出综述、关系、缺口与后续问题，全部带来源。
5. 用户决定是否沉淀为新笔记或日记条目。

### 8.5 被纠正 → 教训沉淀

1. 会话中出现纠错、重问、撤销编辑或否定回答等失败信号。
2. Ratel 提炼一条候选教训（反模式 / 检查项 / 偏好约定），标注来源会话。
3. 候选进入洞察收件箱，用户接受、编辑后接受或拒绝。
4. 接受后写入记忆系统；后续会话经分层注入生效。
5. 用户可随时在记忆面板编辑或删除该教训。

### 8.6 生态管理

1. 用户描述需求（如“我想要看板管理任务”）。
2. Agent 检索社区插件清单，给出带作者、下载量与理由的推荐。
3. 用户确认后，Agent 备份 → 下载 → 安装 → 运行时启用，即装即用。
4. 需要配置时，Agent 读取该插件配置、解释结构，确认后做最小 diff 修改。
5. 出问题或反悔时，用户从变更日志一键回滚到变更前状态。

## 9. 隐私与安全模型

### 9.1 数据范围

- 默认采用黑名单模型：本机可扫描未被排除的 Vault 内容。
- `.ratelignore` 是强制排除入口；后续可增加私密目录/标签 UI，但必须收敛为同一策略判断。
- 黑名单内容不得进入索引、候选检测、模型上下文、日志或 MCP 参数。
- “本地可扫描”不等于“可发送给模型”；EvidenceRef 必须记录披露级别。

### 9.2 最小披露

- 模型只接收完成当前任务必要的片段、结构信息与记忆约定。
- MCP Server 只接收具体工具调用所需参数；Ratel 不把整个会话或 Vault 自动转发。
- 每条洞察和回答可查看使用来源、模型端点和 MCP 外发信息。

### 9.3 主动场景安全

- Heartbeat 只能生成洞察，不能直接调用写入、覆盖、移动或删除工具。
- 用户从洞察发起写入时，仍使用现有工具权限和 Write Gate。
- Notice 只展示最小摘要，不展示被标记为敏感的正文片段。
- MCP 密钥进入系统钥匙串，不进入 `data.json` 或日志。
- 笔记内容、MCP 结果与 Skill 输出均视为不可信输入，不能改变系统权限。
- Skill、MCP 与 Subagent 继承当前会话数据范围，不得形成权限旁路。

### 9.4 审计

本地审计至少记录：触发规则、读取来源、披露目的地、模型/MCP、通知投递、工具调用、确认、执行结果与错误。审计内容默认不复制完整正文，只记录必要摘要与稳定标识。

生态管理操作是审计重点：每次安装、更新、卸载、插件配置修改与启用清单写入，都必须记录动作、目标、前后摘要与备份位置（`EcosystemChange`）。

### 9.5 生态管理安全

- 网络出站仅发生在用户发起生态操作时（GitHub 清单获取与 release 下载）；清单本地缓存，默认 7 天；
- 路径白名单为 adapter 层物理校验，不依赖模型自觉或 prompt 约束；
- 恶意插件防线：只装商店清单内插件、确认弹窗展示作者与下载量、最终决定权在用户；
- 所有环境变更先备份后执行；备份与变更日志存本地插件目录，不进 vault、不出网。

## 10. 运行与降级语义

| 状态 | 行为 |
|---|---|
| Obsidian 正常运行 | 完整 Heartbeat、洞察生成、状态栏、Notice 与收件箱处理 |
| Obsidian 未运行 | 不计算、不投递新洞察；当前阶段不提供常驻后台服务 |
| 插件刚启动 | 恢复未处理洞察；按过期与去重策略决定是否补充提示，不重复弹出旧 Notice |
| 模型不可用 | 保留本地候选与失败原因，不生成伪简报；按退避策略重试 |
| 索引未就绪 | 可使用明确路径的安全只读能力；涉及全库判断的主动规则跳过 |
| MCP 不可用 | 库内能力继续；明确告诉用户外部证据缺失 |
| 商店数据源不可用 | 已装插件的配置管理与回滚继续可用；发现与安装明确告知网络失败，可重试 |

若未来需要 Obsidian 关闭后仍运行的常驻服务或外部消息通道，必须单开 PRD、ADR 与安全规格，不得在当前插件内隐式扩张边界。

## 12. 错误处理与恢复

- Heartbeat 失败不生成空洞察；记录失败并指数退避。
- 日记路径不存在时先询问或建议创建，不擅自创建。
- 月度目标不存在时仍可生成昨日简报，不把缺失等同于用户失败。
- Notice 投递失败不改变洞察为“已读”；用户仍可从状态栏和收件箱处理。
- 插件重载后不得重复弹出已投递 Notice；过期洞察不补发。
- 用户确认写入后执行失败，必须展示已完成和未完成范围，不自动重试副作用。
- 来源笔记在生成后被删除或移动时，显示来源不可用，不复用错误路径。
- 模型输出缺少来源映射时，降级为来源列表并标注，不能伪造编号。
- 下载或安装中断时清理半成品目录，不留损坏安装；无法清理时明确告知用户残留位置。
- 安装后启用失败时回滚到变更前状态并告知原因，不留“装了但不可用”的悬置状态。
- 商店清单拉取失败时使用本地缓存并标注数据日期；缓存不可用时明确说明无法探索，不影响已装插件的本地管理与回滚。
- 修改其他插件 data.json 写入失败时保证原文件未被破坏；已破坏时自动恢复备份并告知。

## 13. 非功能要求

- **性能:** Heartbeat 本地判断不得阻塞主线程；全库重活复用现有索引/调度，不同步遍历正文。
- **可靠性:** 主动规则、洞察和投递状态必须持久化并可从插件重载恢复。生态变更日志与备份状态持久化，插件重载后可继续查看与回滚。
- **安全:** 外部工具结果与笔记内容都按不可信输入处理。
- **可访问性:** Obsidian UI 支持键盘、减少动态效果和可读状态；通知不依赖颜色表达状态。
- **i18n:** 所有新增用户可见字符串进入 `zh.ts` / `en.ts`，命令、Notice、Modal、工具显示名无硬编码。
- **可观测性:** 无遥测；诊断与审计只保存在本地，可由用户查看和清理。
- **兼容性:** 不改变商店三文件发布约束；主动能力全部运行在现有 Obsidian 插件边界内。

## 14. 成功指标

### 14.1 Dogfood 指标

- 连续 14 天中，至少 10 天成功生成一次不重复的每日洞察。
- 每日洞察被接受、写入、继续追问或主动稍后的比例达到 60% 以上。
- 被标记“无关/打扰”的比例低于 10%。
- 用户回答“没有该约定”后，重复主动询问次数为 0。
- 被接受教训对应的偏好，重复犯错次数为 0。
- 黑名单泄漏和未确认写入次数均为 0。
- 生态变更（安装/更新/卸载/配置修改）100% 留有日志与备份；回滚成功率 100%。
- 未经确认的 `.obsidian` 路径写入次数为 0。

### 14.2 产品质量指标

- 100% 主动洞察显示触发原因和来源。
- 100% 由主动洞察发起的写操作经过现有权限确认。
- Obsidian 运行期间，洞察持久化与本地通知投递成功率达到 95% 以上；失败可见且可恢复。
- 插件重载和任务重试导致的重复 Notice 次数为 0。
- 知识挖掘结论至少由两个独立来源支撑；单一来源时必须明确标注。
- 100% 生态变更可在对话中追溯动作与备份位置，并可完成回滚。

这些指标用于验证价值与信任，不上传遥测；由本地诊断面板汇总，用户自行查看。

## 15. README 与传播设计

### 15.1 当前问题

现有 README 已清楚说明图谱、检索、扩展、模型与隐私，但仍存在以下传播问题：

- 首屏“图谱原生 AI Agent”偏技术类别，未直接描述用户每天获得什么；
- “为什么是 Ratel”把产品能力与底座能力平铺，缺少层级；
- 缺少一个能在十秒内理解的完整主动场景；
- Skill、MCP、模型可换等高级能力出现过早，容易让普通知识工作者觉得配置复杂；
- 缺少真实 UI 截图或短动图证明简报、来源、工具和收件箱体验。

### 15.2 建议首屏

- **中文主标题:** 让你的 Obsidian 知识库主动工作。
- **中文副标题:** Ratel 会理解你的日记、目标和双链笔记，在合适时间带着来源复盘、提醒、治理并协助行动。
- **英文主标题:** Make your Obsidian knowledge work proactively.
- **英文副标题:** Ratel understands your journals, goals, and linked notes, then brings you sourced reviews, suggestions, and actions inside Obsidian.

首屏 CTA：`Install from Obsidian`、`See how it works`、`Read the privacy model`。

### 15.3 README 信息架构

1. Hero：一句结果 + 一张“昨日简报/洞察通知”真实截图。
2. 一个完整场景：月度目标 → 昨日日记 → 今日建议 → Obsidian Notice → 确认写入。
3. 三个产品支柱：主动智能、图知识管理、生态管理。
4. 为什么可信：本地筛选、黑名单、最小披露、来源与确认。
5. 开放底座：模型自由、Skill、MCP、Subagent；放在价值之后。
6. 能做什么：找回、治理、挖掘、主动复盘、搭环境（“说一声就装好”）五类真实 prompt。
7. 安装与五分钟上手。
8. 隐私数据流图。
9. 文档、Roadmap、贡献与 License。

### 15.4 文案语气

- 自信但不夸大：不把 wikilink 宣称为高质量领域知识图谱。
- 具体而非抽象：使用“昨天完成了什么、今天该关注什么”等场景语言。
- 技术细节作为证据，不作为首句：先讲用户收益，再讲 ONNX、MCP 与能力池。
- 主动但克制：强调“在合适时间”“带着来源”“修改前确认”。

## 16. 竞品与差异化

| 类别 / 代表 | 强项 | Ratel 不应复制的主叙事 | Ratel 的差异方向 |
|---|---|---|---|
| Smart Connections | 本地语义关联与写作流中的相关笔记 | “更好地找到相关笔记” | 在可靠找回之上主动复盘、治理和挖掘 |
| Obsidian Copilot | Vault Agent、模型自由、Skills 与知识工作流 | “功能最全的 Obsidian AI” | 把开放底座服务于主动图知识管理 |
| Agentic Chat / Intelligence Assistant | 工具、图谱、记忆、MCP、Subagent 与安全执行 | “Obsidian 内的通用自主 Agent” | 记忆约定 + Heartbeat + 洞察收件箱 + 克制的本地通知 |
| NotebookLM / 独立研究助手 | 来源驱动研究与多种成果格式 | “上传资料后做一次研究” | 直接生长在长期 Vault 与日常工作上下文中 |

差异化必须靠真实闭环证明，不能只在 README 中声明“主动”。最小可信演示是：用户无需发起提问，Ratel 基于既有记忆与日记生成带来源的昨日简报，通过 Obsidian Notice 提醒，用户进入洞察详情追问并批准写入今日日记。

生态管理是竞品均未覆盖的空档：现有 Obsidian AI 插件都把“发现、安装、配置插件”留给原生 UI 与用户手动操作。Ratel 用对话完成“需求 → 推荐 → 安装 → 配置 → 回滚”闭环，并与主动智能衔接（如基于工作流缺口建议插件），构成结构性差异。

## 17. 影响面

| 区域 | 预期影响 |
|---|---|
| `src/core/` | Heartbeat、规则状态、洞察、通知策略与审计；生态变更日志（EcosystemChange）与备份管理 |

| `src/tools/` | 治理候选与知识挖掘能力；生态管理工具组（探索/安装/配置/更新/回滚） |

## 18. 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| 通知疲劳 | 用户关闭主动能力 | 本地预筛、每日上限、安静时段、冷却和反馈学习 |
| 黑名单泄漏 | 严重隐私事故 | 单一策略入口、全链路测试、默认拒绝与审计 |
| Prompt Injection | 笔记或 MCP 文本诱导越权 | 不可信输入标记、权限不由文本改变、工具参数验证 |
| Notice 容量有限 | 完整洞察被截断或难以处理 | Notice 只放摘要，点击进入洞察收件箱 |
| 插件重载 | 重复提醒或状态丢失 | 投递状态持久化、稳定洞察 id 与去重 |
| 记忆约定过时 | 错误简报或持续失效 | 来源可见、用户主动 supersede、失败不反复追问 |
| 错误教训被接受 | 持续错误行为被固化 | 教训必经用户审阅、标注来源会话、可随时编辑删除 |
| Obsidian 未运行 | 无法生成新洞察 | 当前阶段明确只承诺应用运行期间主动能力 |
| 恶意/低质插件被安装 | 用户环境受损或数据风险 | 只装商店清单内插件、确认弹窗展示作者与下载量、决定权在用户 |
| 配置修改破坏其他插件 | 目标插件行为异常 | 点名 key 最小 diff、事前备份、一键回滚 |
| GitHub 限流或不可用 | 安装/更新失败 | 清单缓存、明确错误提示、可重试；本地管理与回滚不受影响 |
| 路径白名单被绕过 | 越权写入 `.obsidian` | 白名单为 adapter 层唯一物理入口，测试覆盖路径穿越用例 |
| 产品范围过大 | 长期无法形成可用闭环 | 后续 plan 按完整用户旅程垂直切片，不按技术组件横切堆积 |

## 19. PRD 验收标准

- 产品定位明确为“主动智能的 Obsidian 知识与环境管理 Agent”。
- 主动智能、图知识管理与生态管理是产品支柱；模型、Skill、MCP、Subagent 是开放底座。
- 知识挖掘被纳入图知识管理，不被当作首要日常刚需。
- 当前阶段以 Heartbeat、洞察收件箱、状态栏和 Obsidian Notice 形成完整本地主动闭环。
- 生态管理形成“需求 → 推荐 → 确认安装 → 配置 → 可回滚”闭环；环境变更的信任链完整：路径白名单物理校验 + 事前备份 + append-only 变更日志 + 一键回滚。
- 网络出站扩展（GitHub 清单与 release）有独立 ADR 评审；README 隐私说明同步更新。
- 外部消息通道不属于当前范围，待本地主要特性稳定后再单独评估。
- 黑名单 + 最小披露 + 工具权限 + 审计形成完整信任链。
- 主动场景复用现有记忆与 Obsidian 日记，不新增强制任务数据库。
- README 传播从功能清单改为结果、场景、产品支柱、信任证据与开放底座的层级。
