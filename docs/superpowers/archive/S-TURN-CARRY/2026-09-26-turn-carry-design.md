# S-TURN-CARRY — 思考写了计划、正文过短时再写一次

> 日期: 2026-09-26
> 状态: Active
> Spec ID: **S-TURN-CARRY**
> 关联: [ADR-020](../../adr/2026-09-27-turn-completion-guard.md)、[S-LOOP-STABILITY](2026-09-26-loop-stability-design.md)（完全空步、步数用尽、工具超时）

---

## 1. 这次实际发生了什么

开发预览库里一场对话有 836 条消息。用户发「继续」之后：

- 分类大约 27 秒，再大约 80 秒才出第一个字。
- 日志是 `ask.end`。没有报错，存档里也没有「因长度限制被截断」。
- 助手正文只有一行章标题。思考过程大约一千二百字，结尾是准备写四千到五千字。正文没有写出来。

思考模式把计划放在 `reasoning`，把给用户看的字放在 `content`。模型在正文里输出标题后正常结束。循环把「这一步没有下一个工具」当成答完。标题算有内容，所以也不会走「完全空步再续一次」。

## 2. 压缩为什么不在这次修

自动压缩默认开着，阈值是上下文占用 **85%**。侧栏气泡不删，只给模型看的投影换成摘要加最近原文。85% 是窗口将满前的最后一道。这场对话压缩没有跑，估计占用低于 85%，但日志没有具体百分比。

把门槛改成 50% 没有从这次停笔里量出来。提前压缩也不会让已经正常收笔的模型把标题写成正文。本次维持 85%，不新增更早的阈值。

历史思考继续回传。请求带工具时，思考模式要求后续轮次带回 `reasoning_content`，剥掉会有 400 风险。

## 3. 别的 Agent 怎么做

别人已经做成循环护栏、并且封顶的，是这几类：完全没字就再问，进度套话不当成结束，待办没做完就再推一次。`finish_reason: length` 的自动续写是输出被切断，这场不是。Claude、Cursor、Codex 的自动摘要解决的是上下文太长。

决策见 [ADR-020](../../adr/2026-09-27-turn-completion-guard.md)。

## 4. 目标

1. 可见正文过短、思考更长、且没有写入笔记时，同一轮自动再请求一次，把正文写出来。只给一次。
2. 不要求用户原文必须是「继续」。
3. 聊天里的气泡不删，不另插一条用户气泡。

## 5. 非目标

- 不改 85% 自动压缩，不加 50% 触发。
- 不从请求里剥掉历史思考。
- 不删侧栏消息。
- 不把默认步数从 50 调大。步数用尽、工具超时、完全空的一步，仍归 S-LOOP-STABILITY。
- `finish_reason: length` 仍只追加截断提示（ADR-004），不在这里自动续写。
- 不替用户决定章节大纲。提示语只要求把刚规划的正文写出来。

## 6. 需求

| ID | 需求 | 验收口径 |
|---|---|---|
| TC-01 | 短正文再写一次 | 本步没有工具调用，结束原因是 `stop` 或流正常结束但没有给出结束原因（现有循环把这两种都当成答完）。可见正文至少 1 个码点且少于 200，思考过程更长，本轮没有成功的 `write_note` / `edit_note` / `append_note`：自动再请求一次。提示语是：按你刚写的计划，把正文写出来；不要再重列提纲。同一轮用户消息只一次。`length`、`content_filter`、取消、接口错误不推 |
| TC-02 | 不该推的不推 | 可见正文为空、已不少于 200 字、思考不比正文长、本轮已成功写过笔记、或已经推过一次：不推 |
| TC-03 | 用户能看见续写 | 不另插用户气泡。已写出的短正文与思考照常入库。球仍在转，直到第二次请求结束 |

## 7. 详细设计

在「没有工具调用就结束」之前调用纯函数判断。满足 TC-01 则本步助手消息照常入库，置「已推过」，下一次模型请求前在投影末尾加一条不写入会话的 `system`。用完即丢。推过一次仍短，按现在结束。

可见字数按 Unicode 码点计，不含思考。

## 8. 影响面

| 区域 | 变化 |
|---|---|
| `src/core/turn-carry.ts` | 短正文判断与提示语 |
