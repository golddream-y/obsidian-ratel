## 过程失误（按责任排序）

**1. 我把「测试全绿」当成了「能启动」的证据。**

三轮实施每轮都以「全量 3068 passed / 0 failed」收尾，我据此认为风险已收敛。但那些用例验证的是单元语义，**没有一条覆盖「给定磁盘状态 → 代际记录 / 活动指针 / Ready 三者是否一致」**。两次事故都精确落在这个空洞里：一次是「已提交」与「仍在构建」互相矛盾，一次是「97 篇提交完成但从未激活」。全绿只证明改对了函数，不证明插件能起来。

**2. 我在自审里批准了一条没有证据支撑的捷径——这是最直接的责任点。**

Task 7 为了让 `autoIndex=false` 时显示 Ready，加了「空 layout（`blockCount=0`）= 已提交的空库」。我批准时只问了「这样合理吗」，没问「这个结论和代际记录的状态冲突时会发生什么」。而 `layout.blockCount` 在新建库恒为 0，等于**任何新建代际在首次索引前都会被宣告已提交**。自审的价值在于追问反例，我把它做成了确认。

**3. 首次真实宿主验证同时变了三个变量。**

分片布局 + 线程模式 + 清空索引一起上。卡死时无法二分：是布局没被识别、还是线程装配失败、还是空库判定错误。正确顺序是一次只变一个：先用主线程验证布局，再开线程。事故 2 之后我正是靠「关线程、留分片」才定位到两个问题互不相关。

**4. 装配层接线缺少对齐清单。**

`createFirstCommitPromoter` 只在 `index-runtime-assembly.ts:496` 接线这件事，Task 6 的报告里就提到过那个行号，我读到了但没有把「两条装配路径的横切逻辑是否等价」当成检查项。最后发现它靠的是现场证据，不是流程保证。

**5. 并行会话共享分支却无交接。**

我在不知情下为已完成任务派了 subagent；开工前没有先用 `git log` 核对计划复选框与实际提交。

## 做对的地方

- **每次事故都保留现场**：隔离 `gen-*.hang-*`、保留 `control.json.hang`、用 worktree 留存分片前基线，既能回滚也能取证。
- **判定依赖磁盘证据而不是印象**：`activeGenerationId`、`status`、`verifiedAt`、shard 数、receipt 数逐项读，两次定位都直接来自这些字段。
- **没有为了变绿改测试**：写量阈值那处争议是先改判据（改为「平均 ≤ 全库/N×1.2 且单次最大 ≤ 最大片×1.2」）再改断言；空布局那处是把用例改成反向断言。
- **隔离边界守住**：全程只碰 Sandbox，生产库始终是 `ae54f3ba`。

## 可执行的改进

1. **装配对齐清单**：任何「主线程 + 线程」双路径的横切逻辑（提权、恢复、清理、只读守卫、清单读写），必须两边都接线或显式声明不适用，并各有一条用例。
2. **启动闭环用例**：以磁盘状态为输入，断言「代际 status / `activeGenerationId` / 管理器是否 Ready」三者一致。两次事故都在这一格，值得单独成组。
3. **宿主验证一次一个变量**：布局（主线程）→ 线程模式 → 清库重建，按序推进，每步留下读数。
4. **自审改问法**：对每条捷径/特例，必须回答「如果它错了，症状是什么、会被哪条用例抓到」，答不上来就不批准。
5. **并行会话交接**：开工前 `git log` 核对计划复选框与实际提交，避免重复派活；共享分支时先确认对方已完成范围。

## 结论

分片索引本身按设计工作（97/97、`active`、8 片、写量降到约 1/7），但把它送到可用状态的过程暴露了三个更根本的问题：**测试全绿被当成可运行证据、自审被做成确认、宿主验证多变量同时变**。这三条与分片无关，会影响后面每一个改动，优先级高于任何功能实现。
