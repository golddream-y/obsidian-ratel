最重要的实测事实(第 5.3 节给出推导)。**这里有两个彼此独立的缺陷,必须分开表述**
(此前的合并表述「对任何耐久实现都不可达」只在小库档成立,大库档不成立):

1-a. **耐久性溢价(独立缺陷,只在小库档结构性存在)**。T0 基线用的是 vectra 默认存储 ——
    每次写入不 `fsync` 也不同步父目录。把 T1 的原子存储注入到**未改动的旧路径**上,
    100 篇完整构建就从 585 ms 涨到 2735 ms(**同一窗口 A/B = 4.67×**;
    **规范审查的独立复跑 = 5.93×**,两次方向一致)。这一项与本次设计无关,是 T1 存储策略引入的
    固定成本;它**随库变大而收敛**:`t0-durable / t0` 在 1000 / 3000 篇只有 **1.46× / 1.12×**。
    即「耐久性溢价让门槛不可达」只在**小库档**成立。
1-b. **记录基线与本轮数据口径落差(另一个独立缺陷,全档约 1.5～2×)**。未改动的旧路径 `t0`
    在本轮窗口里也是 T0 记录基线的 **1.98 / 1.86 / 2.04×**(100 / 1000 / 3000 篇)。
    来源是**语料与机器口径**,不是任何实现退化:本轮语料每篇 **7 块**(320 字符 / maxTokens=100),
    T0 记录约 **4.7 块/篇**;100 篇的 `index.json` 本轮 **1.09 MiB** vs T0 **471.5 KiB**;
    且 T0 是带载采集、其负载读数并未记录。按计划字面「≤ 1.5 × T0 成功基线」，
    这一落差在本轮窗口内就让**任何**臂都难以达标 —— 与「是否耐久」是两件事。
2. **本次设计的附加成本随库变大而收敛**:对耐久性对齐基线,`coordinator / t0-durable` 在
   100 / 1000 / 3000 篇分别是 2.90 × / 1.85 × / **1.44 ×**。差距集中在**小库**档,
   而小库正是用户最常见的起点;来源是每文件新增的 **4 次小型耐久写**(分片、`prepared.json`、
   完成记录、catalog),合计字节只占总量 **0.07%** —— 代价在次数,不在字节。
3. **峰值内存与写放大都不是问题**:峰值 RSS 三档相对 T0 记录都是 0.87 – 1.29 ×(门槛 1.5 ×);
   `index.json` 写入字节与「旧路径 + 同一存储」相差不到 1%;累计写入耗时亦已按类别记录(第 4 节)。

### 2.2 重样本门控(必须说明的口径取舍)

基础配置 `vitest.config.ts` 的 include 是 `tests/**/*.test.ts`,因此**它同样会收集本文件**。
3000 篇 @64 维的完整构建在本机约 11–12 分钟;若这些用例无条件执行,`npm test` 会从约 2 分钟
涨到 15 分钟以上(T0 对同类大样本用的也是环境变量门控)。度量依据:未门控的 4 例
(512/768 维各 120 篇、连续编辑、隔离区回收、夹具自检两例)实测**合计 36.5 s**
(逐用例 28957.7 + 7194.2 + 306.0 + 2.4 ms,取自同一次运行的 JSON 报告),
而单是 3000 篇 @64 维一次完整构建本轮实测 **584–587 s**。

因此本文件有三级门控:

| 门控变量 | 来源 | 打开的内容 |
|---|---|---|
| `RATEL_SCALE_SUITE=1` | **专用配置** `test.env` 自动注入 | 重样本:3000 篇 @64 维(含零变化三连测)、300/400/200 篇级写入行为、队列内存探针 **+ 100 篇档三臂 A/B(checkbox 4 的判定口径)** |
| `RATEL_SCALE=1` | 显式环境变量 | 上述全部 **+** 1000 / 3000 篇 A/B 与 512 维读数表(`RATEL_SCALE_XL=1` 再打开 512 维 3000 篇) |
| (无) | 基础配置 `npm test` | 只跑结构性用例:夹具自检(含门槛可比性自检)、512/768 维各 120 篇、连续编辑、隔离区回收 |

关键路径(规范审查 I2):计划要求的执行命令是
`npx vitest run --config vitest.index-reliability.config.ts`(**不带** `RATEL_SCALE`)。
100 篇档 A/B 由此成为默认口径的一部分 —— 否则该命令只产出 22 passed / 7 skipped,
**一条门槛读数都不产生**、checkbox 4 的判定没有出口。100 篇档约 35 s,与 3000 篇档的重门控互不影响。

计划 checkbox 2 要求的「3000 篇 + 512/不同维度」在**专用配置的默认口径**下全部执行(见第 3 节),
`npm test` 只是不重复这份 12 分钟成本。这一取舍不影响任何验收断言,但在证据里必须写明。

关键实现选择及其理由:

- **另起一份管线装配,而不是扩展 `index-crash-child.ts`**:规模用例需要往 `createStorage` 注入计数实现,
  而 T8a 的 `assembleIndexHarness` 按崩溃阶段硬编码了该工厂。给它加参数会改动 T8a 已交付、
  并被其证据文档逐行引用的文件;两份装配都只调用生产入口 `setupWritableIndexRuntime`,
  差异仅是注入的存储实现,已在代码注释里写明。
- **计数存储只累加聚合计数、不保存逐次事件**:3000 篇会产生 1.5 万次写入,
  保存事件数组会让「内存有界」的断言把观测器本身变成被测对象。
- **大库流式落盘**:`generateAndWriteNotes` 逐个生成并立即写盘,只返回路径列表;
  端口(`createCountingVault`)只暴露路径与按需 `readFile`,不暴露任何正文集合。
  这是「不得为全库预先构造正文数组」的结构性保证,第 6.3 节给出运行时内存证据。

逐项断言与实测:

- **完整构建无重复嵌入(已提交版本无重复计算)**:`嵌入调用 === 非空文件数`(3001 === 3001)、
  `嵌入文本 === 期望总块数`(21670 === 21670)。任一文件被重复嵌入都会让调用数大于文件数。
  可计数端口是直接观察点(`DigestCountingPort.calls/texts`),不是从耗时反推。
- **嵌入文本多重集合等式(规范审查建议 7,本轮下沉到 3000 篇档)**:`512 维/768 维` 用例把端口记录的
  **全部嵌入文本**与「同一分块器 + 同一正文」的期望文本排序后逐项比较(840 条);
  3000 篇档用同一比较口径的**摘要版本**:端口逐条记录嵌入文本的 sha256 前缀 64 位(21670 条 ≈ 0.17 MiB,
  不保留正文),与独立算出的期望摘要多重集合**逐项相等**。
  「等块数的文件互相冒名」这种只比条数时可以被抵消的情形,会让摘要集合不等;
  `批次数 === 文件数`(120 / 3001)另作结构断言。
- **块集合逐文件相等**:按 ID 序列(`<path>#chunk-<i>`)比对首页、中位页与超长文件的磁盘块集合,
  不只比数量(只比数量会让「旧块残留 + 新块写入」互相抵消)。
- **超长文件**:`writeBigChunkNote` 按分块器实测收敛,最终 600 块(要求 > 200)。
- **连续编辑**:同一路径连续编辑 5 次与 25 次,**热点路径的读取次数都是 4**,总读取都是 43。
  读取次数不随编辑次数增长 —— 队列按路径只保留最新项(若逐事件处理,该数字会随编辑次数线性增长)。
  提交数为 1(其余 39 篇零重新嵌入),完成记录 `inputHash` 等于末版正文 hash,磁盘块集合等于末版期望。
- **多次重启**:连续 3 次零变化启动(72 / 64 / 59 ms),嵌入调用均为 0,写入计数均为 0,
  索引根目录的**每文件字节数与内容 sha256** 均不变(旧实现只比字节数却写成「逐字节」,本轮已订正)。
  3000 篇档另有零变化三连测,见下文「零变化启动订正读数」一条。
- **读取不是全库预构造**:3000 篇完整构建期间 `vault.readFile` 被调用 **9003 次 / 3001 条路径**
  (恰好每篇 3 次:核对一次 + 推理后与提交前各核对一次),而**零变化启动恰好每篇 1 次**
  (探针实测 3000 次 / 3000 条路径)。读取是「按需读单篇 + 用完即弃」,端口不持有正文集合。
- **队列/事务/并发上界(确定性计数)**:`maxInFlight` / `maxConcurrentPrepares` / 转移点磁盘
  `pending/` 峰值 / `maxConcurrentEmbeds` 全部 ≤ 1,且「转移点磁盘目录项数 ≠ 在途事务数」次数为 0
  (计数点与磁盘核对方式见第 6.3、6.4 节)。`maxQueued` 在 vault 步进点读取,是**下界**,
  3000 篇实测 3001(等于文件数,即按路径合并后的天然上界),只作说明、不作上界断言。
- **写入量(3000 篇 @64 维)**:累计 **15014 次 / 49.1 GiB**,其中 `index.json` **3001 次 / 49.0 GiB**
  (即「每文件一次全量重写大 JSON」,与 T0 的机制一致,计划 T2 的「不得增加每提交写入次数」成立);
  其余约 12013 次由 catalog、分片、`prepared.json`、完成记录构成(每文件约 4 次小型耐久写)。
  **累计耗时(规范审查 I4)**:计数存储按类别累计 `ms`,`index.json` 一类的累计字节数与累计耗时
  由**同一次构建**同时给出(100 篇档与单文件事务档见第 4.1 / 6.2 节);1000 / 3000 篇档的
  `ms` 需要重采,命令见第 8.1 节(本轮未重采,不把旧字节数配上新耗时)。
- **`maxQueueEntries` / `compactMemory` 口径**:协调器的队列上界默认 `100000`、按路径合并,
  本轮 3001 篇的 `queued` 峰值等于文件数,远低于上界;`compactMemory` 的保留依据是
  「本轮枚举 ∪ 队列 ∪ 未决事务 ∪ 已核实 ∪ 溢出」(`src/core/index-task-coordinator.ts` 的 `compactMemory`),
  规模会话的 `total` 因此只表达本轮已知文件数,不随历史路径增长。
  **本用例不修改生产默认上界**:生产装配不暴露 `maxQueueEntries` 注入点(只有直接构造协调器时可选,见
  `tests/core/index-task-coordinator.test.ts` 已验证的小上界用例),因此这里只断言「不超过文件数」这一更强的规模上界。
- **真 ONNX**:不跑。门控变量 `RATEL_ONNX` 只在基础配置里控制 `tests/adapters/embedding-onnx.test.ts`,
  专用配置的 include 面从不包含它;本轮未改这一现状,也未新增 ONNX 门控(见第 8 节)。

已修复为「装配返回的真实代际目录」。门控运行重采的读数不再有这个缺陷,
本文件不把修复前的 0 当作「索引文件为空」的证据。

> **未在同一口径下验证(采样期间负载高于核数,带载读数不作为门槛依据)。**

修复轮复采落在负载 5.7 – 8.2 的窗口(三臂高点 6.26 / 6.26 / 6.36,均 ≤ 核数 10),
所以「负载高于核数」这一条在修复轮不再成立;但**计划字面口径仍然不可比** ——
分母(T0 记录)没有负载读数,分母臂无法核对(下面第 2 点)。

**可比性核对覆盖两个臂(规范审查 I3)**:`judgeGate` 现在同时记录并校验**分子臂**(被测的
`coordinator`)与**分母臂**(基线)的负载,判定结果里始终带出两侧负载文本。
分母臂有两类:

1. **同窗口的 `t0-durable`**(耐久对齐分母):它是本次采集的另一条臂,**有负载读数**,
   因此可以和分子臂一样被核对;
2. **T0 记录基线**:T0 证据没有记录负载数字(只自述为「带载采集」),分母臂负载记为
   **「未记录」** —— 此时无法核对「同一口径」,判定同样必须是 `not-comparable`。
   **不把「分母臂没有读数」当成「分母臂合格」。**

`judgeGate` 的实测输出(三个规模档都是同一结论;这是修复轮前的采集,分母臂负载当时还没有记录):

```
[T8b 门槛 plan]            样本=100  → 三项全部 not-comparable,"负载最高 11.45 高于核数 10"
[T8b 门槛 durable-matched] 样本=100  → 同上
[T8b 门槛 plan]            样本=1000 → 三项全部 not-comparable,"负载最高 10.53 高于核数 10"
[T8b 门槛 plan]            样本=3000 → 三项全部 not-comparable,"负载最高 23.79 高于核数 10"
```

修复轮由**计划命令默认口径**复采的 100 篇档判定(原文见第 7.1 节):分子臂负载 6.36 **≤ 核数**,
分母臂 `t0-durable` 6.26 ≤ 核数,因此**耐久性对齐口径给出了可比判定**;
而分母臂 = T0 记录的那一套**仍然不可比**,原因只剩「分母臂没有负载读数」这一条。

两点必须如实说明:

1. 负载判据用的是**总负载**,其中包含**测量进程自身**的贡献(测量进程是一个 CPU 密集线程,
   在 10 核机器上约贡献 1.0)。修复轮 100 篇档的分子臂负载最高 6.36(外部约 5.4),
   第一次满足了「负载 ≤ 核数」——这正是该档能给出可比判定的原因;上一轮三档则不满足,
   本文件不把上一轮的读数判为达标。
2. 结论不会因此变得不可用:同一窗口内的**对照臂比值**对负载不敏感(两臂在同一窗口、同一机器、
   同一数据、同一分块器、同一假嵌入、每臂三次取中位数),第 5.2 节据此给出方向性判定,
   并明确标注它**不是**计划的字面门槛。
3. **零变化启动的 100 篇档不给门槛判定**:两个分母都低于可判定下限(100 ms)——
   T0 记录 14 ms(1.25 × = 17.5 ms)、修复轮同窗口 `t0-durable` 10 ms(1.25 × = 12.9 ms),
   都落在本机计时抖动内;该档判定值为 **`absolute-only`**(只报绝对值,见 7.1)。

#### 5.2.1 修复轮 100 篇档:计划字面口径不可比,耐久对齐口径首次可判定

修复轮复采(负载 6.26 – 6.36,**全部 ≤ 核数 10**)的判定原文见 7.1。三项结论:

| 耐久性对齐(分母 = 本次 `t0-durable`) | **8132 / 2766 = 2.94 × → `fail`(未达标)** | 482.8 / 482.4 MiB = **1.00 × → `pass`** | 分母仅 10 ms,低于可判定下限 → **`absolute-only`(只报绝对值 35 ms)** |

**结论方向不变**:小库档的完整构建在耐久对齐口径下**仍未达标(2.94 ×)**;
峰值 RSS 达标;零变化启动在 100 篇档**不再给门槛判定**(分母低于计时分辨率,
绝对值 35 ms vs 10 ms 仍如实列出,约为 3.5 ×,但不作为门槛结论)。
同时新增一条如实记录:**计划字面口径至今没有一次可比判定** —— 因为 T0 记录基线没有负载读数。

3000 篇零变化启动的订正依据见第 4.3 节:门控运行里的 5532.5 ms 是负载伪影;
修复轮已把该读数做成**仓库内可复现**(命令 = 计划命令本身),两次独立复采的中位数是
**590 ms / 597 ms**(负载 8.15 / 6.49,均 ≤ 核数),对 T0 记录的 683 ms 是 0.86 – 0.87 ×。
**上一轮那个来自仓库外临时探针的 650.9 ms 已作废**(仓库内无产物、不可复现)。
即便如此,该档在**计划字面口径**下仍判 `not-comparable` —— 分母臂(T0 记录)没有负载读数,
无法核对「同一口径」;因此本文件**不把 0.87 × 写成达标**。

**关键观察(两个独立缺陷,分开读)**:`t0 / T0 记录` 这一列在上一轮三个规模档分别是 1.98 / 1.86 / 2.04
(修复轮 100 篇档复采是 **1.53 ×**)—— 即**未改动的旧路径**在本轮窗口里也是 T0 记录基线的 1.5 – 2 倍。
这是**记录基线与本轮数据口径的落差**:本轮语料每篇 7 块(T0 记录约 4.7 块/篇)、
100 篇 `index.json` 本轮 1.09 MiB(T0 471.5 KiB),且 T0 是带载采集、其负载读数并未记录。
它**不是**「耐久性」造成的,也不随实现变化。

另一件事是**耐久性溢价**:把 T1 的耐久存储注入到**未改动的旧路径**,100 篇完整构建就从
585 ms 涨到 2735 ms(上一轮同一窗口 A/B 4.67×;**修复轮复采 450 → 2766 ms = 6.15×**;
规范审查独立复跑 5.93×),而 1000 / 3000 篇只有 1.46 × / 1.12 ×。
所以「对任何耐久实现都不可达」这类合并表述**只在小库档成立**;
按计划字面「≤ 1.5 × T0 成功基线」,大库档的困难主要来自上面那条 1.5 – 2 倍的口径落差,而不是耐久溢价。

把这两项分别扣除后,上一轮窗口内的净结论(方向不变;100 篇档的修复轮判定见 5.2.1):

| 门槛项 | 100 篇 | 1000 篇 | 3000 篇 |
|---|---|---|---|
| 完整构建(对耐久对齐基线) | 2.90 ×(修复轮 2.94 ×)未达标 | 1.85 × 未达标 | **1.44 × 方向性达标** |
| 峰值 RSS(对 T0 记录) | 1.05 × 达标 | 1.29 × 达标 | 1.07 × 达标 |
| 零变化启动(对 T0 记录) | 只报绝对值(分母低于可判定下限) | **0.86 × 达标** | 0.87 × 只报比值(分母臂无负载读数) |

**差距集中在 100 篇这一档**:完整构建 2.90 – 2.94 ×,规模越大越接近门槛。

### 5.3 成本结构(为什么差距是结构性的,而不是抖动)

100 篇、64 维时,代价与**耐久原子写的次数**几乎成正比:

| 臂 | 原子写次数 | 其中索引 | 单次构建耗时 | 每次耐久写 |
|---|---|---|---|---|
| `t0`(非耐久 `writeFile`) | 102 | 102 | 585 ms | 5.7 ms |
| `t0-durable` | 204 | 102 | 2735 ms | 13.4 ms |
| `coordinator` | 500 | 100 | 7921 ms | 15.8 ms |

规模变大后,每次写的**字节量**成为主导(3000 篇时 `index.json` 单次重写 33 MiB),因此
「每次耐久写」的单价从 100 篇的 13–16 ms 涨到 3000 篇的 42–74 ms;但结构结论不变:

1. **索引文件写放大没有增加**(计划 T2 的硬约束成立)。每文件仍是 **1 次 `index.json` 全量重写**;
   与「旧路径 + 同一条耐久存储」相比,字节数在 100 / 1000 / 3000 篇分别是 +0.7% / +0.7% / +0.79%。
2. **本次设计新增的是每文件 4 次小型耐久写**(分片、`prepared.json`、完成记录、catalog):
   100 篇 500 − 204 = 296 次 ≈ 每文件 3 次;1000 篇 5000 − 2004 = 2996 次;3000 篇 15000 − 6004 ≈ 8996 次。
   这些写的数据量极小(3000 篇合计约 36 MiB = 总写入量的 0.07%),成本来自**次数**(每次一次
   `fsync` + 父目录同步),不来自字节。
3. **耐久性本身值 4.67 倍(100 篇,同一窗口 A/B;规范审查独立复跑 5.93 倍)**;
   随着单次重写字节量变大而收敛到 **1.46 ×(1000 篇)、1.12 ×(3000 篇)**。
   这一项与本次设计无关,是 T1 存储策略引入的固定成本,而 T0 基线完全没有这一项;
   它是**独立的缺陷①**,且**只在小库档**构成「门槛不可达」的理由。
   与之独立的缺陷②是记录基线与本轮数据口径的约 1.5～2 倍落差(第 5.2 节),
   它对所有臂一视同仁,不是耐久性造成的。
4. **本次设计的附加成本同步收敛**:2.90 × → 1.85 × → 1.44 ×。
   **结论:差距在「小库」这一档最严重,而小库正是用户最常遇到的起点。**

因此「零变化启动在 100 篇未达标」这一表述**本轮已按分辨率规则改写**:100 篇的零变化核对几乎全是固定开销
(代际解析、写所有权租约、日志恢复、逐文件 hash 核对),分母只有 10 – 14 ms —— 1.25× 门槛 = 12.5 – 17.5 ms
落在计时抖动内,**因此该档只报绝对值、不给门槛判定**(见 5.2.1);
1000 篇对 T0 记录基线反而是 0.86 ×。3000 篇的零变化读数已在本仓库内复现
(590 / 597 ms,负载 ≤ 核数),但计划字面口径仍因分母臂无负载读数而不给判定。

### 5.4 门槛口径的结论

- 按计划字面门槛(分母 = T0 记录的**非耐久**采集):**三个规模档的完整构建都未达标**;
  峰值 RSS 三档达标;零变化启动只有 1000 篇给出达标判定,100 篇因分母低于计时分辨率只报绝对值,
  3000 篇因**分母臂没有负载读数**不给判定。
- 按耐久性对齐分母(同一窗口的 `t0-durable`):完整构建在 3000 篇方向性达标(1.44 ×),
  100 / 1000 篇未达标(2.90 / 1.85;修复轮 100 篇档复采 2.94 × 且**该档负载 ≤ 核数,判定为 `fail`**);
  零变化启动 100 篇只报绝对值(分母 10 – 13.8 ms),1000 / 3000 篇未达标。
- **「同一口径」判定**:上一轮三档一律 `not-comparable`(负载高于核数);修复轮的 100 篇档
  在负载 ≤ 核数下**首次给出可比判定**(完整构建 `fail`、峰值 RSS `pass`),
  但计划字面口径**从未**产生可比判定 —— 因为分母(T0 记录)没有负载读数。
- 门槛口径本身存在缺陷:第 5.3 节第 3 条证明,把 T1 的耐久存储注入到**未改动的旧路径**上,
  100 篇就已超出门槛 4.67 – 6.15 倍。继续用非耐久基线当分母,会把「是否耐久」误报成「设计是否退化」;
  但这条现在只作为**小库档**的缺陷①陈述,不再写成「对任何耐久实现都不可达」。

## 6. 写入行为断言的逐条证据(checkbox 5)

### 6.1 零变化启动不写向量数据

- **同一实例**第二轮(不是重新装配,排除装配期写入被误算):写入计数 **0 次**,
  其中索引 0 次、分片 0 次、`prepared.json` 0 次、完成记录 0 次,且各分类的累计写入**耗时也为 0**
  (计数存储按类别的 `ms` 与 `count` 同口径);
  索引根目录快照(`相对路径 → {字节数, 内容 sha256}`)**按内容比对不变**(旧实现只比字节数却表述成「逐字节」,已订正),无 `.tmp-` 残留。
- 300 篇 + 超长文件的**跨实例**重启 3 次:每轮 `diffSnapshotContents` 均为
  `{added:[],removed:[],changed:[],resized:[]}`(修复轮实测 60 / 68 / 65 ms,负载 6.58),
  写入计数增量 0,嵌入调用 0。
- 该断言覆盖整个索引根(含 `generations/` 控制指针与 `owner.lock`),不只是向量文件。

### 6.2 单文件变化只提交一次该文件事务

200 篇、改第 8 篇后重启再核对(计数在同一实例上先清零)。修复轮复采把**累计耗时**一并列出
(规范审查 I4):

| 分类 | 次数 | 字节 | 累计耗时 |
|---|---|---|---|
| 索引文件 `index.json` | **1** | 2.2 MiB | **12.4 ms** |
| 完成记录 `files/<hash>.json` | **1** | — | — |
| `pending/<id>/prepared.json` | **1** | — | — |
| 分片 `pending/<id>/part-*.json` | **1** | — | — |
| **合计(全部类别)** | **5** | **2.2 MiB** | **56.4 ms** |
| 嵌入调用 | **1**(6 条文本 = 该文件 6 块) | — |

`indexed === 1`(其余 199 篇零重新嵌入),提交完成后 `pending/` 目录项为 0,
磁盘块 ID 序列等于新内容经同一分块器的期望。
即:T2 要求的「删除与插入在同一事务内、单文件只落盘 1 次」在本设计的生产路径上成立
(T0 修复前为 2 次,见 T0 证据第 5、10.2 节)。

### 6.3 队列只存路径/序号,不保留全库正文

- **结构守卫**(与 T0 同口径的静态文本扫描,能力边界已注释):`interface QueueEntry` 的字段体中
  不含 `content` / `text` / `body` / `blocks` / `vector` / `embedText` / `snapshot`;
  协调器源码中不存在任何 `private ...Snapshot|content|contents|bodies|texts` 字段
  (`CoordinatorSnapshot` 含 `content`,但它必须是**局部变量**,一旦成为字段就退化为在途快照常驻)。
- **事务边界确定性计数**(生产装配 + 日志接缝,取代采样):`assembleScaleHarness` 经装配层公开的
  `wrapJournal` 接缝装饰生产日志,在**每个状态转移点**(`prepare` 进入/返回、`commit`、`cleanup`)
  计数在途事务数与 `prepare` 并发数,并在同一转移点**直接读磁盘**核对 `pending/` 目录项数。
  嵌入端口侧同样在 `embed` 进出点计数。确定性结论见 6.4。
- **运行时内存探针(降级:只作观测,不作为独立结论)**。此前该探针断言
  `堆增量 < 语料增量 / 4`;但三次实测的堆增量都是**负值**(−39.5 / −22.0 / −14.3 MiB),
  该不等式对负值**恒真**,因此它**不能**作为「内存有界」的独立证据(代码质量审查 I5)。
  现已降级:探针仍运行并打印读数,但**不再断言**;该条可用的证据只有上面的结构守卫与
  事务边界确定性计数。探针设置与三轮历史读数(仅作观测):

  | 轮次 | 小语料 / 堆峰值 | 大语料 / 堆峰值 | 语料增量 | 堆增量 |
  |---|---|---|---|---|
  | run 1 | 5.9 MiB / 130.8 MiB | 133.4 MiB / 91.3 MiB | +127.5 MiB | **−39.5 MiB** |
  | run 2 | 5.9 MiB / 107.8 MiB | 133.4 MiB / 85.8 MiB | +127.5 MiB | **−22.0 MiB** |
  | run 3 | 5.9 MiB / 120.8 MiB | 133.4 MiB / 106.4 MiB | +127.5 MiB | **−14.3 MiB** |

  设立方式:固定 3000 个文件,只改每篇正文字符数(1 KB → 24 KB),分块端口**丢弃正文**(返回零块),
  日志用内存替身(不落盘),因此索引与日志都不随语料增长。**该探针不能证明「内存有界」** ——
  堆峰值受 GC 时点与负载影响(三轮 ±20 MiB),负增量只说明这一次采样没捕捉到增长。
- **大样本不预构造正文数组**:3000 篇的合成与读取只经过「路径列表 + 按需 `readFile`」,
  端口不暴露任何正文集合(结构保证),读取计数见第 3 节(完整构建 9003 次 / 3001 条路径);
  三次 3000 篇完整构建的峰值 heap 147.9 / 146.2 / 146.3 MiB、
  峰值 RSS 494.9 / 524.8 / 530.7 MiB,而语料本身只有约 1.7 MiB、索引文件 33 MiB ——
  峰值由索引序列化决定,不随语料线性增长。这不是分配器级证明,只是结构与量级证据。

### 6.4 未结算事务只保留活动文件(确定性计数,非采样)

401 篇(+超长文件)档,计数点覆盖全部事务状态转移(vault 访问步进点 + 日志 `prepare`/`commit`/
`cleanup` + 嵌入进出点),不使用 20 ms 定时采样:

| 观测 | 依据 | 上界 | 实测 |
|---|---|---|---|
| 在途事务(`maxInFlight`) | 日志状态转移点计数 | 1 | 1 |
| `prepare` 并发(`maxConcurrentPrepares`) | 日志状态转移点计数 | 1 | 1 |
| `pending/` 目录项(转移点**磁盘真值**) | 每次转移读磁盘 | 1 | 1 |
| 转移点「磁盘目录项数 ≠ 在途事务数」次数 | 同上 | 0 | 0 |
| 嵌入并发(`maxConcurrentEmbeds`) | `embed` 进出点计数 | 1 | 1 |
| `queued` | vault 步进点读取(**下界**,只作说明) | 文件数(按路径合并) | 3001(3000 篇档) |
| 运行结束磁盘 `pending/` 目录项 | 运行结束读磁盘 | 0 | 0 |

「同一时刻只有一个活动项」在 20 ms 采样口径下只能得到下界,因此本条以前不能作为上界断言;
改成确定性计数后,`maxInFlight` / `maxPendingDirs ≤ 1` 才是可判定的事实。

### 6.5 已结算但清理失败的分片可定位回收

### 8.2 需 Lead 裁定

**裁定项 1(最高优先):门槛口径必须修订,或明确改判为「口径不成立」。**

依据(**两个独立缺陷,分开陈述**):

- **缺陷①:耐久性溢价 — 只在小库档构成「门槛不可达」**。把 T1 的耐久存储注入到**未改动的旧路径**,
  100 篇完整构建从 585 ms 涨到 2735 ms(**同一窗口 4.67×;规范审查独立复跑 5.93×**)。
  但 `t0-durable / t0` 在 1000 / 3000 篇已收敛到 **1.46 × / 1.12 ×** ——
  大库档**不成立**「对任何耐久实现都不可达」。
- **缺陷②:记录基线与本轮数据口径落差 — 全档约 1.5～2×**。`t0 / T0 记录` 在 100 / 1000 / 3000 篇
  分别是 1.98 / 1.86 / 2.04 ×,来源是语料块数(本轮 7 块/篇 vs T0 约 4.7)与机器状态,
  且 T0 的负载读数未记录。它与「是否耐久」无关。

两者合起来才会得到「≤ 1.5 × T0 记录基线不可达」的观感;分开看,小库档确实是**两个缺陷叠加**
(1.98 × 的口径落差 × 4.67 × 的耐久溢价),而大库档主要是②在起作用。
继续沿用非耐久基线当分母,会把「是否耐久(①在**小库**的影响)」与「口径落差(②)」
一起误报成「设计是否退化」,因此门槛口径仍需修订;但**不得**再用「对任何耐久实现都不可达」的合并表述。

建议(可并用):

- **修订分母**:相对门槛的分母改为「同一分支、同一数据、同一负载窗口的 `t0-durable` 对照臂」,
  `t0`(非耐久)只用于报告「耐久性带来的绝对增量」,不参与判定。本次三档的
  `coordinator / t0-durable` = 2.90 × / 1.85 × / 1.44 ×,**修订分母后 100 与 1000 篇仍未达标**。
- **补充绝对预算**:为「3000 篇 @64 维完整构建 ≤ X 秒 / 峰值 RSS ≤ Y MiB / 累计写入 ≤ Z GiB」
  设绝对门槛,本轮已给出 64 维与 512 维两套绝对值。
- 把三臂对照固化为专用配置的一个可复现用例(本轮已实现为 `性能口径与相对门槛` 的 `abAt`)。

**裁定项 2:是否按计划「优化或修订存储设计」。**

我方判断:**需要优化,但不是换存储**(spec 明确不换数据库;第 4、5 节证明 `index.json`
写放大与「旧路径 + 同一存储」相差不到 1%,本次设计没有增加全量重写成本)。

真正的成本来源已经定位到**每文件的耐久原子写次数**:本次设计每文件 5 次
(1 次 `index.json` + 分片 + `prepared.json` + 完成记录 + catalog),旧路径 + 同一存储是 2 次。
这些新增写的字节只占总量的 0.07%,成本全在「每次一次 `fsync` + 父目录同步」的延迟上。
这解释了为什么差距随库变大而收敛(2.90 → 1.85 → **1.44**):小库里固定延迟摊不开,
大库里单次 `index.json` 重写的字节量把它淹没了。

候选动作(按性价比排序):

1. **只在提交点耐久(建议优先)**。分片与 `prepared.json` 是**可重算的暂存数据** ——
   T3 已把「没有 `prepared.json` 的事务」定义为不可重放、启动时重算;
   对它们保留原子 rename(不产生半截文件)但**跳过 `fsync` 与父目录同步**;
   向量提交(`index.json`)与完成记录保持完全耐久。按第 5.3 节的次数结构,每文件耐久写 5 → 2 次,
   预计把小库档的 2.90 × 压到 1.5 × 内。
   **风险与前置条件**:这改动落在 T1 的 `AtomicIndexStorage`(已审查、已交付的实现面),
   必须重新论证 spec A6「IO 故障 / 掉电」语义没有被放宽(原子性不变、只降低暂存数据的**掉电耐久性**),
   并需要 Lead 裁定 + 一轮定向审查。**这是本轮唯一需要改动 `src/` 的建议。**
2. **完成记录改为追加日志**(每条一次 append + 定期聚合),消掉每文件一次的小文件原子写;
   代价是恢复路径要新增日志解析与截断处理。
3. **保留现状,改用绝对成本预算**(裁定项 1 的第二条)。

我方倾向:先做第 1 条,第 2 条列为后续任务;若 Lead 不接受改动 `src/`,
则采纳第 3 条并把本轮绝对值作为基准。

**裁定项 3:小库档是否需要单独的产品判断。**

100 篇档的完整构建在耐久对齐口径下**未达标**(上一轮 2.90 ×、修复轮可比判定 2.94 × `fail`),
而 1000 / 3000 篇已经达标或接近;零变化启动在 100 篇档**不再给门槛判定**
(分母 10 – 14 ms 低于可判定下限,只报绝对值 35 ms vs 10 ms),但绝对值同样指向小库档的固定开销。
「小库」正是新用户首次建立索引、以及日常小库用户每次启动的路径。若目标里包含「小库启动体验」,
裁定项 2 的第 1 条就从「优化」变成「必须」。

**裁定项 4:重样本门控的取舍是否可接受。**
