# 写放大与流畅度：两项待办的判断

> 计划：[P-ADAPTIVE-INDEX](2026-11-02-adaptive-indexing.md) · 验收：[T9 协议](2026-11-02-adaptive-indexing-t9-protocol.md) · 进度：[实施进度](2026-11-02-adaptive-indexing-progress.md)

## 1. 写放大（已量化，未修）

读数（效率基准，文件系统层计数）：

| 文件数 | 累计写入 | 每篇 | 目录最终体积 |
| --- | --- | --- | --- |
| 50 | 722 KB | 14.8 KB | 47 KB |
| 100 | 2691 KB | 27.6 KB | 94 KB |
| 200 | 10392 KB | 53.2 KB | 189 KB |

文件数翻倍 → 写入涨约 3.8 倍，即 O(N²)。根因：Vectra 的本地索引每写一条就要重写整份索引文件。

### 为什么 M1 不修

M1 的目标是「索引期间 Obsidian 能正常使用」，写放大属于**存储效率**，与主线程卡顿不是同一件事；而且在当前规模下每篇耗时仍平坦（74–77 ms），尚未成为耗时瓶颈。把它塞进 M1 会让一个已经很大的改动再背上存储格式变更的风险。

### 可选方案（按风险从低到高）

1. **批量提交**：索引期把 N 个文件的向量写入合并成一次 `beginUpdate/endUpdate`。写量降到 O(N)，改动集中在会话与日志的提交边界；风险是「批内单文件失败」的语义要重新定义（当前是逐文件完成记录）。
2. **日志追加 + 定期压实**：向量以追加段写入，启动或空闲时压实。写量接近线性，但检索要跨段合并，读路径复杂度上升。
3. **分片索引**：按路径哈希分片，每片独立文件，写量按片摊薄。实现改动最大，检索需要多片查询。

建议：作为 M2 之后独立 spec 处理，先做方案 1 并用本基准的写入字节作为验收口径（判定线建议「每篇写入 ≤ 3× 单篇数据量」）。

## 2. 流畅度：唯一还缺的宿主读数

### 操作步骤

1. 调试构建（已就绪）：`RATEL_INDEX_EXPERIMENT=1 node esbuild.config.mjs production`，并已链接预览库（`main.js` / `manifest.json` / `styles.css` / `worker.js` 均指向本仓库 `dist`）。
2. 在 Obsidian 预览库中**重载插件**（或重启应用）。加载后 5 秒会自动跑一次实验，命令面板入口保留。
3. 报告写入系统临时目录：`ratel-index-thread-experiment-*.json`（新文件名带时间戳）。

### 判读方法

- `selfCheck.maxGapMs` ≥ 250：探针可信，否则整份报告作废。
- 流畅度通过条件：`runtime.stall.maxGapMs` **明显低于** `mainThreadIndex.stall.maxGapMs`（同一台机器、同一份两篇笔记的负载）。
- 若两者接近：说明在该负载下索引本来就不卡，**不能**据此宣称线程化解决了卡顿，需要把负载调大到能复现卡顿（更大索引或更多文件）再测。
- `reopen.found` 必须为 `true`，否则落盘持久性在该环境不成立，正确性组同样不通过。

### 为什么不能替代

隔离代理（Node worker 线程）在 50/300/800 三档读数不稳定，已记录为否定结果；宿主里的 Blob Worker 与 Node worker 是不同实现，且真实卡顿来自 Obsidian 渲染进程，只能在宿主里测。
