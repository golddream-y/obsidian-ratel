# S-SHARDED-INDEX 分片向量索引设计

需求：`BUG-1-INDEX-PERF-001`。关联 [S-ADAPTIVE-INDEX](2026-11-02-adaptive-indexing.md)（线程与可靠性）与 [写放大记录](../plans/2026-11-02-adaptive-indexing-write-amplification.md)。本文替代 S-ADAPTIVE-INDEX 中「单份 `index.json`」的存储前提。

## 背景

生产库 2961 篇笔记，代际目录下的 `index.json` 已达 **231 MB**（约 1.98 万个块）。vectra 的本地索引以整份 JSON 落盘，任何一次提交都要重写整个文件。

2026-11-04 的实测与生产读数：

| 场景 | 读数 |
| --- | --- |
| 100 篇逐篇提交（主线程） | 8389 ms，写入 2691 KB，`index.json` 重写 **100 次** |
| 100 篇两阶段批量（线程） | 6128 ms，写入 220 KB，重写 **1 次** |
| 生产库当前 | 1336 / 2961 篇，`index.json` 231 MB，进程 RSS 峰值 **2.0 GB** |
| 生产库推进速度 | 18 分钟仅 +6 篇，最近一次完成记录后 6 分钟无新进展 |

两阶段批量提交已把「重写次数」降到 1/N，但**单次体积仍是 231 MB**：序列化与落盘成本随库规模线性增长，进程内存压力（2 GB RSS）带来的 GC 同时拖慢界面线程——表现为滚动尚可（合成器线程处理）而点击、关闭等需要主线程的操作明显卡顿。

结论：瓶颈已从「写次数」转为「单次写入体积」。不改存储布局无法解决。

## 目标

1. **单次提交的写入字节与耗时不再随全库规模线性增长**：写量与总块数的比值由 O(1) 变为 O(1/N)。
2. **索引期间主线程可响应点击**：索引写盘不再制造超过 100 ms 的主线程长任务（以探针取样为准）。
3. **不改变正确性契约**：逐文件完成记录、代际与配置指纹、检索结果语义、崩溃恢复与「未变文件零重复嵌入」全部保持。
4. **不重嵌入迁移**：既有单文件索引可一次性就地拆分，复用已有完成记录与向量。
5. **不做物理合并**：查询侧以内存归并产出单一有序 `topK`，不把分片写回单份 `index.json`；否则一次改动的提交又要重写全库，收益立刻归零。

## 非目标

- 不改 `manifest`、文件日志、完成记录与代际格式。
- 不做向量量化、二进制编码或更换存储引擎（体积优化另立 spec）。
- 不改检索融合、可见性门与精排策略；分片只影响候选来源。
- 不追求磁盘总占用下降（分片后总量与单文件基本持平）。
- 不做物理合并与后台压缩（LSM 形态留作后续；分片是写入真相，查询不依赖任何合并产物）。

## 详细设计

### 分片键与布局

- 分片数**自适应**并写入代际布局元数据（`shards/layout.json`），**不进入配置指纹**：指纹描述内容（模型/分块/维度），分片数是存储布局，改它只需重分布，不应触发重嵌入判定。
- 取值规则：`N = clamp(2^ceil(log2(总块数 / 2048)), 8, 64)`。2961 篇约 1.98 万块 → 16 片（单次约 14 MB）；100 篇约 1.5 千块 → 下限 8 片（约 0.9 MB）。小库不用 64 片，避免扇出与文件数压过收益。
- 片数变化只允许通过重分布完成（读旧布局 → 写新布局 → 原子切换），不重嵌入。
- 分片键：`shardId = firstByte(sha256(规范化相对路径)) % 16`，与 journal 的 `pathHash` 同源，保证**同一路径的所有块永远落在同一分片**。
- 布局：`<generation>/shards/<00..0f>/index.json`（每片是一个独立 vectra 本地索引目录）。代际目录仍是备份、清理与「不可删除活动代际」判定的单位，布局变化不外溢到代际管理。

### 写入

- 单文件提交只打开目标分片，`replaceFile` 只在片内删除旧块、写入新块。
- 批量提交按 `shardId` 分组：每组一次 `beginWriteBatch`/`endWriteBatch`，仍保持两阶段顺序（**先落盘块、再写完成记录**）。
- 跨分片批次最多产生 16 次写，但每次只写该片；单次体积上限约为总索引的 1/16。

### 读取与查询

- 候选召回分两轮，**磁盘上不做任何排序，也不做物理合并**：
  - 第一轮（片内）：对本片全部块线性扫描余弦，用大小为 `K` 的堆维护片内 `topK`；
  - 第二轮（跨片）：把 `N × K` 个候选做 k 路归并，输出全局有序 `topK`（`N=16, K=20` 时约 320 个候选，微秒级）。
- 每片取 `topK` 是**充分且精确**的：一片最多贡献 `K` 个，取多了是浪费。对调用方始终是一份有序 `topK`，扇出不外溢。
- 同一文件命中多个块时，去重/取最高分/相邻块扩展属于展示层的结果整形，不属于本 spec，语义不变。
- 分片查询可并行发起；失败的分片必须显式升级为错误，不能当成「该片为空」静默降级。
- `inspectFile(path)` / `inspectFiles(paths)` 先按 `shardId` 路由到目标分片，避免全量枚举。

### 迁移

1. 启动时若检测到「单份 `index.json` 且无 `shards/`」，进入迁移：读取旧索引，按 `shardId` 分组写入各分片。
2. 逐片校验块数与块集合校验和；全部通过后写标记并保留旧文件为 `index.json.legacy`（不立即删除，供回滚）。
3. 任一步失败则保持旧布局可用（fail-closed），下次启动重试；迁移不调用嵌入模型。
4. 迁移完成后旧 `index.json` 不再被读取；清理动作与已有「清理非活动代际」一致。

### 崩溃恢复

- 沿用两阶段语义：中断最多留下「有块无记录」，由既有恢复决策补写完成记录。
- 分片损坏的影响面限定在该片内路径；恢复按完成记录逐路径判定，不因单片异常隔离整个代际之外的范围。

### 验收判据

| 维度 | 判据 |
| --- | --- |
| 写量 | 单次提交写入字节 ≤ 全库索引体积 / 16 × 1.2；2961 篇档全量重建总写入不高于单文件布局的 1/8 |
| 流畅度 | 索引期间主线程长任务（>100 ms）数量与最长值显著低于单文件布局基线，点击/关闭可用 |
| 正确性 | 同一查询、同一 `topK`，分片布局与单文件布局结果逐条一致；迁移后未变文件零重复嵌入 |
| 恢复 | 分片写入中断后重启，完成记录与块集合一致，块集合校验和通过，嵌入调用为 0 |
| 兼容 | 代际目录结构、控制指针、`manifest` 与文件日志格式不变；旧布局可直接打开并迁移 |
| 无合并产物 | 索引目录中不存在合并后的单份 `index.json`；增量提交后未变路径零重复嵌入 |

## 影响面

- `src/adapters/vector-vectra.ts`：分片路由、批量写、跨片查询合并、旧布局检测与迁移。
- `src/worker/index-runtime-session.ts`：批量提交按分片分组，保持两阶段顺序。
- `src/core/index-runtime-assembly.ts`、`src/core/index-thread-assembly.ts`：装配分片存储而非单实例。
- 索引目录文件数从 1 个 `index.json` 变为 16 个，备份/清理入口需按目录语义确认（代际目录为单位的逻辑不变）。
- 效率基准与 T9 效率组：写量口径改为「单次写字节 / 全库体积」，需补 2961 篇档对照。
