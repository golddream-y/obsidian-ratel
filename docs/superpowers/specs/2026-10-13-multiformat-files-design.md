# 大批量多格式文件管理迭代方案

> ID：S-MULTIFORMAT-FILES · 日期：2026-10-13 · 状态：Active（首版设计草案，尚未实施）
>
> 本方案让库内的笔记、表格、演示稿和文档共同参与检索。先建立本地文字与结构缓存，提供精确搜索、语义检索和来源定位，再验证大批量文件的资源消耗。Office 编辑、图片识别和其他产品方向另行讨论。

## 1. 背景与目标

用户已经把 Excel、PPT 等工作材料放入 Obsidian，希望在同一个工作区中管理项目知识。文件存进库只是第一步：助手还需要发现文件、读到内容、找到证据，并跟随原件更新。

以 develop 的 1.1.0 为基线，当前文件索引主要枚举 Markdown；grep 也只扫描 Markdown 正文。默认本地嵌入模型是 bge-small-zh-v1.5，512 维、输入上限 512 tokens、每批最多 16 段。现有文字模型可以继续使用，但 Office 文件不能直接交给它处理。

本次迭代的目标是：**保留原件，把可提取的文字和结构转成可重建的本地缓存，让精确检索和向量检索共享内容，并把结果定位回原文件。**

用户应能完成这样的任务：“查找这个项目的预算依据，列出相关笔记、预算表位置和方案页码。”本期负责找到与核查证据；自动核算预算或修改 Office 原件不属于本期交付。

### 范围与非目标

| 格式 | 首期内容范围 | 明确限制 |
|---|---|---|
| Markdown、TXT | 正文与位置；Markdown 继续保留标题和链接关系 | 保持现有笔记行为兼容 |
| PPTX | 原生标题、正文、文本表格、演讲者备注及页码 | 不识别图片文字、图表视觉含义或动画；不承诺复现版式 |
| XLSX | 工作表、表头、单元格范围、可读取的值与公式 | 不执行宏、不重算公式；缓存值可能过期或缺失 |
| DOCX | 段落、标题、表格及可恢复的结构位置 | 不承诺稳定页码；复杂浮动布局不作为定位依据 |
| PDF、CSV | 后续格式批次评估；CSV 优先复用表格结构，PDF 区分可提取文字与扫描件 | 首批不承诺支持，纳入下一批前补覆盖与验收范围 |

旧版二进制 Office 格式、加密文档、损坏文件和未知格式先登记状态，明确提示不支持或解析失败。不能把失败解释成“没有内容”。隐藏工作表和备注属于额外读取范围，默认不纳入索引；用户明确启用后才提取，并在结果中标识。批注、嵌入对象与外部数据连接首期不解析、不执行、不刷新。

本期不建设完整 Office 编辑器，不自动转换并替换原件，不默认全库 OCR，不把整个文件发送给模型，不扩大库外访问权限，不迁移现有索引引擎或选定新的解析依赖。

## 2. 详细设计：原件与可检索内容

### 内容处理全貌

```text
库内文件发现 / 变动补查
          ↓
稳定性检查 → 本地格式解析 → 带来源位置的内容缓存
                                     ├─ 精确 / 关键词搜索
                                     └─ 结构分块 → 文字 embedding → 语义搜索
                                                       ↓
                                    读取命中片段 → 核查原文件与对应位置
```

几十兆 PPT 的文件体积不能直接用于估算向量化成本。图片、视频等可能占据绝大多数体积，向量化只消费提取出的文字。解析器仍需要限制压缩包展开大小、条目数量和文本输出量，避免把大文件全部展开到内存中。

### 缓存的职责与数据

原始文件是唯一正文来源；内容缓存不用于恢复原件，也不是另一份需要用户维护的笔记。它存放于插件本地数据目录，可清理、可重建，不默认生成大量可见 Markdown 副本。清理缓存不改变原文件。

每个文件记录内部标识、库内相对路径、格式、大小、修改时间、处理代次、解析器及其版本、提取策略、最近成功处理时间和覆盖范围。来源身份与路径分开：收到重命名事件可保留身份；离线期间的移动若无法唯一识别，按删除旧路径、发现新路径处理，不能仅凭同名或相同体积认定同一文件。

解析结果由内容块与来源映射组成。PPTX 保留页码和块类型；XLSX 保留工作表名、单元格范围、表头与公式/缓存值的区别；DOCX 保留标题路径、段落或表格位置。来源位置与文件版本一起保存，不能把旧文件第七页当成新版本第七页。

同一块保留两种表达：用于精确匹配的提取文字，以及用于语义检索的结构化文字。前者避免随意改写，后者可补入文件标题、页标题、表头和必要上下文。二者都指向同一来源；搜索界面说明匹配的是提取内容，缓存行号不能伪装为 Office 原件行号。

数字、公式和工作表关系必须保留，不只保存模型生成的摘要。超大工作表不得整表塞入一个片段，应按连续范围分段并携带表头；超长页或段落同样拆分。模型 token 上限要实际检查，不能把“500 字符”视为必然低于“512 tokens”。

### 文件管理与覆盖状态

所有格式都可进入文件清单，但只有支持且在用户索引范围内的格式进入解析队列。按格式和目录选择索引范围，延续现有排除规则；插件自身缓存、配置目录和 Office 临时文件不得成为索引来源。

清单分别呈现发现、排队、解析中、可精确搜索、向量化中、完整就绪、部分覆盖、内容过期、失败和不支持。文字可搜索不必等待向量化完成。用户能看到为何未覆盖、重试单个文件或重新解析，并暂停整批任务。

## 3. 详细设计：变动检测与增量更新

### 事件与启动补查

继续通过 ObsidianVault 外观接收创建、修改、重命名、删除事件。事件是更新线索，不是文件已经写完的证明。按文件去抖，重复检查大小与修改时间，等待稳定后再解析；过滤锁文件、临时文件和保存中间产物。稳定等待和重试均须有上限，持续变化的文件延后处理，不阻塞整批。

启动时遍历文件元数据，与上次清单比较，补齐应用关闭期间的变化。大小和修改时间是快速筛选，不是内容相同的强证明：提供手动强制重新解析和有预算的校验机制，覆盖同步工具保留时间戳等情况。首期具体校验策略及频率在实现选型时确定。

### 一次更新的提交条件

1. 文件事件更新处理代次，同一文件队列中只保留最新待办。
2. 确认文件稳定，记录源文件快照信息，再解析到暂存结果。
3. 解析结束后复核源文件信息及处理代次；期间变化、移动或删除则丢弃过期结果，重新排队。
4. 发布新的文字缓存和来源映射，让精确检索可用；来源代次必须一致。
5. 分块比较内容指纹，复用未变化的向量，仅处理变化块。指纹包含实际嵌入输入、模型和预处理版本，不能只用页码或文本长度。
6. 发布新代次的向量索引，移除失效块；查询不得将旧向量、旧原文与新位置拼成一条证据。

内容未变化时更新文件检查记录及必要的来源映射，不重复嵌入。移动整页或调整表格位置时，即使可复用文字向量，来源映射也必须更新。删除文件使对应内容立即退出检索，并取消在途处理；后到的结果不得让已删除文件重新出现。

解析失败保留上次成功缓存供诊断，但默认检索不以其作为当前证据；用户主动查旧内容时明确显示过期。新文字已发布而向量仍在更新时，旧代次向量不作为当前命中返回，允许暂时只有精确检索。断电或退出后从清单恢复未完成任务，不能显示半次更新为完整就绪。

## 4. 详细设计：批量检索与来源定位

### 精确检索与向量检索共享缓存

当前 grep 的 Markdown 枚举入口需要扩展，但二进制 Office 原件不直接做正文扫描。Markdown 继续按现有约定检索；Office 精确搜索查询本地提取内容，并返回格式对应的位置和覆盖状态。

批量精确搜索不能每次重新解压所有文件。文字查询先做文件范围筛选，必要时建设关键词索引；任意正则匹配仍要按限定范围读取缓存并执行，有扫描量、结果数和执行预算，支持分页与取消。关键词索引与正则扫描不是同一种能力，不承诺所有正则都能通过索引加速。

语义检索只对文字内容分块做 embedding。优先复用现有本地模型，以真实中文项目资料评估效果；不因增加格式就默认升级更大模型。查询以关键词、语义和文件元数据互补，型号、编号和金额等精确条件走文字或结构匹配。链检索继续连接笔记和附件引用，不凭目录相邻、文件同名自动生成确定的知识关系。

Excel 的检索可返回单元格范围，并支持按范围读取供核查；“金额超过阈值”“汇总差额”等结构计算另行设计，不能把相似度排序视为计算答案。

### 来源与覆盖的展示

来源返回原文件路径、格式、版本、定位信息和短片段。例如 `方案.pptx → 第 12 页`、`预算.xlsx → 采购表 → D18:F24`。打开原件和展示定位信息是首期最低承诺；能否在预览器或外部应用中准确跳转到页/单元格，取决于对应能力验证，不能提前宣称已实现。

结果显示提取覆盖：是否包含备注、是否遗漏图片内容、是否有缺失的公式缓存值、是否部分截取。检索汇总同时说明尚未解析、失败或被排除的文件数量。“没有命中”只说明本次已覆盖内容中未找到，不等于整个工作区不存在。

## 5. 详细设计：资源与隐私边界

### 资源控制

文件发现优先只读取元数据；内容按队列逐件加载，避免把全库正文一次放进任务 payload。大文件解析采用有界并发与隔离执行，重 CPU 解析不得阻塞 UI，也不直接塞入现有只做 ONNX 推理的 Embedding Web Worker。解析隔离方式在后续技术验证中决定，并遵守无原生模块与 Obsidian API 外观约束。

分别限制压缩文件体积、解压体积、条目数、提取字符数、块数、工作表范围、处理时长和总缓存体积；超限显示部分覆盖或待按需处理，不能静默截断。向量化采用有界批次，单个巨大文件不得独占队列；用户主动查询的文件可以优先，整批任务支持暂停、取消和恢复。

清理缓存时保留足够状态以触发重建，检索反映尚未就绪。原件修改不自动导致其他未变化文件重建。现有 Vectra/JSON 索引是否适合目标规模，必须按实测的加载内存、写入耗时和查询延迟判断，本方案不把 Float32 理论体积当成真实存储占用。

### 隐私控制

默认在本地解析并沿用本地嵌入配置。启用远端 embedding、重排或对话模型时，提取文字仍可能外发，隐私说明覆盖这一通道。模型只读取完成当前任务所需的片段，不默认携带整个工作簿或整份 PPT。

目录排除、格式范围和隐含内容读取策略同时作用于解析、缓存、搜索和发送。收紧策略后，旧缓存和向量也要立即失效并清理，不允许用历史索引绕过新边界。解析器不执行宏、文件脚本或文档内指令，不自动访问外部引用；提取内容被当作资料，不作为 Agent 系统指令。

本期仅处理库内文件；现有库外访问开关不因新增格式自动开启。缓存与原件一样可能含敏感资料，本地保存不等于加密，也不能把当前模型密钥的加密机制描述为正文加密。

## 6. 分阶段迭代与验收

| 阶段 | 交付 | 验收重点 |
|---|---|---|
| A：代表性样本验证 | PPTX、XLSX、DOCX 的本地提取样例与测量报告 | 结构、覆盖缺口、峰值内存、解析时间、依赖体积与许可；暂不全库启用 |
| B：文字管理闭环 | 文件清单、缓存、事件更新与启动补查、精确搜索、来源定位 | 不解压全库查询；保存/移动/删除/离线修改及失败状态正确；可暂停恢复 |
| C：增量语义检索 | 结构分块、现有 embedding、变化块更新、跨格式检索 | 向量复用、代次一致性、真实检索质量；收紧排除规则后旧数据退出 |
| D：规模与下一批格式 | 多格式批量处理、资源配额和按需解析；评估 CSV/PDF | 达到样本规模目标后再扩格式；需要换索引时另开设计，不夹带迁移 |

先建立不含真实隐私的验收集：文字型 PPT、图片占比高且达几十兆的 PPT、含备注的 PPT、大工作表、公式缓存缺失或陈旧的表格、复杂 DOCX、损坏与加密文件。人工记录预期片段及位置，覆盖中文关键词、同义表达、项目编号和多文件关联。

测量按文件数、提取字符数、内容块数和图片占比记录，不能只报总 GB。逐步验证 100、1,000、10,000 文件的分级样本（可用可重复的合成内容测负载，质量评测仍使用人工验收样本），分别记录冷启动、热启动、单文件更新、精确查询、语义查询、缓存体积、峰值内存及 UI 响应。是否达到万文件目标取决于测量，不是本稿已承诺的容量。

每一阶段同时验证：只改图片且文字不变时不重复嵌入；Office 连续保存不发布半成品；向量化失败不阻塞已有精确检索；删除后无残留命中；重命名不丢来源；策略收紧后旧数据不再可检索或外发。具体机器基线与时间/内存阈值在阶段 A 后写入实施 plan，本稿不虚构性能结论。

## 7. 影响面与待验证决策

这是一项跨模块迭代：VaultPort 增加多格式文件枚举与安全二进制读取能力；新增本地格式解析与内容缓存职责；索引调度支持任务恢复、处理代次和块级更新；grep 与检索结果支持格式定位；聊天引用与状态界面呈现覆盖范围；设置提供索引范围与资源限制。实际接口、模块目录、迁移方式和解析依赖在技术验证后确定，本次只写设计，不改这些契约。

已确定的方向：原件保留、派生缓存可重建、文字先提取后嵌入、精确和语义检索共享内容、版本与来源绑定、增量检测兼顾事件和启动补查、资源有界、失败与覆盖可见。

待验证的决策：各格式解析器与许可、复杂结构保真程度、解析线程隔离、元数据快筛之外的校验策略、持久化与关键词索引选型、当前向量库的容量边界、外部应用或预览器的精确跳转能力。没有完成上述验证前，不编写完整实施 plan，也不把可行性描述成已交付能力。

后续代码落地需同步用户手册、README 和 CHANGELOG 的格式支持与隐私边界；涉及端口、数据模型、线程与索引迁移时按项目规则确认并更新架构说明。
