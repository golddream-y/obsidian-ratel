# S-CHAT-PERF — 聊天流式渲染与块级虚拟滚动设计

> **ID:** S-CHAT-PERF
> **状态:** Active
> **日期:** 2026-08-15
> **关联:** S-MSG-STREAM、S-MD-PREVIEW、S-CHAT-NAV
> **决策:** 性能优先；保留连续打字体验，不保留“每个渲染帧都执行完整富 Markdown”的实现方式。

---

## 1. 背景

当前助手文本的流式路径是：`message.delta` 追加到消息文本，Svelte 把完整 `content` 传给 `MarkdownView`，`MarkdownView` 在 `requestAnimationFrame` 中重新执行 `marked + highlight.js + DOMPurify`，随后替换整段 `innerHTML`，再扫描 Mermaid、引用、代码块和表格并重新绑定交互。

这套实现限制了同一帧的重复刷新，却没有改变“每次刷新都处理全部历史文本”的成本。随着回复增长，第 N 次刷新仍会重新处理前 N 份内容，累计工作量接近平方增长。富块增强、DOM 替换、布局与逐 delta 自动滚动会进一步放大主线程压力。

本次诊断样本使用 16K 字、200 个增量：单次完整渲染约 `37ms`，模拟流式全量重绘累计约 `5.89s`。该数字受机器影响，只作为现状基线；确定性验收以渲染调用次数、DOM 稳定性和复杂度约束为主。

此外，当前消息列表会挂载整个会话。即使单条流式消息不再全量重绘，长会话中的历史 Markdown、工具段、图片和图表仍会持续占用 DOM 与布局资源。因此本设计同时覆盖流式增量渲染和整个聊天区的块级虚拟滚动，但按三个可独立交付的阶段落地。

---

## 2. 目标

1. 长回复流式生成时，Obsidian 侧栏保持可滚动、可停止、可切换笔记，不再因 Markdown 重绘卡死。
2. 保留文字持续增长的打字体验；允许流式阶段延迟 Markdown 高亮、引用按钮和 Mermaid 等富效果。
3. 已完成的 Markdown 块最多富渲染一次，后续 delta 不得重建其 DOM。
4. 长会话只挂载视口附近的渲染单元，并保持滚动条比例、阅读锚点和右侧进度轨语义稳定。
5. 所有优化均有纯逻辑测试、调用次数约束、基准场景和 Sandbox 人工验收。
6. 不改变 Agent Loop、模型事件协议、消息持久化格式和最终 Markdown 内容。

### 2.1 成功标准

- 16K 字、200 个 delta 的流式阶段不再按 delta 次数调用完整 Markdown 渲染。
- 第一阶段每条流式文本段只在结束时执行一次完整富渲染。
- 第二阶段的富渲染次数只与稳定块数量相关，不与 delta 数量相关。
- 已冻结块的 DOM 身份在后续 delta 到来时保持不变。
- 流式阶段不出现超过 `100ms` 的主线程长任务；Sandbox 中滚动、停止和切换笔记保持响应。
- 基准样本累计渲染时间不高于旧实现的 `20%`。该比例作为专项基准门槛，不作为跨机器 CI 的绝对时间断言。
- 最终静态展示与现有 `renderMarkdownToHtml` 的语义一致，代码、表格、引用、Mermaid、复制和放大能力不回归。
- 历史内容超出虚拟窗口后不保留实际内容 DOM，但滚动高度和进度轨位置保持连续。

---

## 3. 非目标

- 不修改 LLM 流式协议、`AgentEvent` 或消息 segment 持久化结构。
- 不把 Markdown 解析、索引或 UI 渲染迁入 Worker。
- 不新增 Markdown 解析或虚拟列表依赖，优先复用现有 `marked`、Svelte 和浏览器 API。
- 不在第一阶段实现稳定块识别或虚拟滚动；紧急止血必须可单独发布。
- 不要求流式中的半截 Markdown 与最终静态 Markdown 完全同形。
- 不在本 spec 内优化模型调用、检索、Embedding、会话压缩或 Obsidian 主窗口性能。
- 不承诺系统级“页面查找”能命中未挂载的虚拟内容；Ratel 自身的会话与知识库搜索不受影响。

---

## 4. 方案决策

评估过三种策略：

| 方案 | 优点 | 缺点 | 决策 |
|---|---|---|---|
| 降低全量重绘频率 | 改动小 | 只减缓平方增长，长文本最终仍卡 | 不采用 |
| 流式轻渲染，结束后富渲染 | 性能收益最大，边界清楚 | 富格式在结束时成形 | 第一阶段采用 |
| 稳定块一次富渲染，活动尾部轻渲染 | 兼顾流畅与富格式 | 边界识别和 DOM 管理更复杂 | 第二阶段采用 |

第三阶段在前两阶段形成的“稳定渲染单元”之上增加虚拟滚动。它解决历史 DOM 膨胀，不替代对活动消息流式重绘的治理。

## 5. 详细设计

### 5.1 总体数据流

```text
message.delta
    ↓
StreamTextBuffer（只接收新增文本）
    ├─ active tail：轻量文本节点增量追加
    └─ stable blocks：一次 Markdown 渲染后冻结
    ↓
RenderUnit[]（消息、工具段、稳定块、活动尾部、系统分隔）
    ↓
VirtualWindow（只挂载视口附近单元）
    ↓
滚动容器 + 右侧进度轨
```

数据层仍以现有 `Message[]` 和 `segments` 为事实源。流式缓冲、稳定块和虚拟窗口都是 UI 投影，不写入会话持久化，也不改变发送给模型的内容。

### 5.2 第一阶段：流式轻渲染

流式文本段进入 `streaming-light` 状态：

1. `message.delta` 继续追加到现有消息数据，保证持久化与上下文逻辑不变。
2. 只有运行中助手消息的末尾文本段是活动流式段；一旦工具、思考段或新的文本段出现在其后，该段立即完成富渲染，不等整轮结束。
3. UI 缓冲本帧新增的后缀，只向活动文本节点追加新内容，不用完整 `content` 覆盖旧 DOM。
4. 文本容器使用 `white-space: pre-wrap` 保留换行；写入必须走 `textContent` 或文本节点，禁止拼接未净化 HTML。
5. 流式期间不调用 `renderMarkdownToHtml`、`renderMermaidBlocks`、`enhanceCiteLinks` 或 `enhanceMdBlocks`。
6. `streaming` 变为 `false` 时，对完整文本执行一次现有富渲染管线，再替换轻量文本 DOM。
7. 用户正在选择该文本时，沿用现有延迟替换策略；松开选区后再完成最终富渲染。
8. 取消、异常和正常结束走同一收尾路径，已收到的文本都必须成为可读的最终内容。

第一阶段是独立可发布的紧急止血版本，也是第二阶段无法识别安全块边界时的永久降级路径。

### 5.3 第二阶段：稳定 Markdown 块冻结

第二阶段引入 `StableMarkdownBlockDetector`，只分析尚未稳定的尾部，不扫描已冻结内容或整条消息。

稳定块遵循保守原则：

- 标题、普通段落、引用、列表、表格等只有在边界明确后才能提升为稳定块。
- 围栏代码必须检测到匹配的闭合围栏；未闭合围栏始终留在活动尾部。
- 表格必须具备完整表头、分隔行和结束边界。
- 列表、引用或其他跨行结构存在歧义时不得猜测，继续保留为轻量尾部。
- Markdown 引用定义等会改变前文解析结果的文档级语法不得跨块冻结；检测到这类依赖时，保留相关文本为单一尾部并在结束时统一渲染。
- 检测器只返回“稳定前缀 + 活动尾部”，不直接操作 DOM，也不负责富渲染。

稳定前缀提升时：

1. 对该块调用一次 `renderMarkdownToHtml` 并追加到稳定块容器。
2. 记录稳定块 id、源码范围和 DOM 引用；后续 delta 不得重建或替换该块。
3. Mermaid、引用、代码复制和块级动作只针对新稳定块执行，不扫描旧块。
4. 活动尾部继续使用第一阶段的文本节点增量追加。
5. 消息结束时完成剩余尾部。实现可对尾部做一次最终富渲染；不得为了收尾重新渲染所有冻结块。

若稳定块检测、渲染或增强失败，保留该块的纯文本内容并继续接收后续 delta。单块失败不得使整条消息白屏，也不得退回整条消息的每帧全量重绘。

### 5.4 第三阶段：块级虚拟滚动

虚拟化单位不能只到消息级。一条超长助手消息本身就可能包含大量 DOM，因此统一使用 `RenderUnit`：

| 单元 | 示例 |
|---|---|
| 消息外壳 | 用户短消息、错误消息 |
| 文本块 | 助手稳定 Markdown 块 |
| 活动尾部 | 当前流式轻量文本 |
| 工具段 | tool call / result |
| 系统分隔 | compact marker 等 |

当前正在生成的消息直接复用第二阶段产出的稳定块。加载历史会话或首次投影静态助手消息时，`RenderUnitProjector` 对完整文本执行一次块划分，生成多个文本单元；划分失败时才把整个文本段作为一个降级单元。块 id 由消息 id、segment 顺序和源码范围稳定派生，不写回消息数据。

静态投影检测到 Markdown 引用定义或其他跨块依赖时，不拆分该文本段，确保虚拟化不会改变最终 Markdown 语义。

同一消息拆成多个虚拟单元后仍保留统一的逻辑消息分组：首块承担气泡顶部和消息锚点，末块承担底部间距，中间块不重复绘制消息 chrome。复制整条消息、辅助功能标签和进度轨锚点都基于逻辑消息，而不是当前挂载的单个块。

虚拟窗口根据真实滚动容器的 `scrollTop`、`clientHeight` 和高度缓存计算可见范围，只挂载视口上下各约 1–2 屏的 overscan。窗口外内容用顶部、底部 spacer 保持总高度和原生滚动条比例。

高度与锚点规则：

- 每个已挂载单元由 `ResizeObserver` 更新真实高度；未测量单元使用按类型估算的高度。
- 图片加载、Mermaid 完成、工具展开和字体变化导致高度变化时，更新缓存。
- 用户位于底部附近时保持 sticky-to-bottom；用户向上阅读时以首个可见单元及其像素偏移为锚点，修正 spacer 后不得跳读。
- 活动流式尾部的数据始终更新；用户位于底部附近时保持挂载。用户向上阅读且尾部离开 overscan 后允许卸载，回到底部时直接挂载最新状态，不能为“保留尾部 DOM”而把中间全部单元重新挂载。
- 用户拖动右侧进度轨时，现有比例先映射到估算总高度；目标单元挂载并测量后进行一次锚点校正。
- 点击进度轨消息锚点时，即使目标尚未挂载，也必须先按 id 定位对应单元，再滚动并短暂高亮。
- 用户正在跨块选择文字时，相关单元加入临时保留集合；选区结束后恢复正常回收。

虚拟化只改变 DOM 投影，不删除 `Message[]` 中的历史内容。会话持久化、复制单条消息、引用打开和重新进入会话仍以完整数据为准。

### 5.5 组件边界

| 单元 | 职责 | 主要依赖 |
|---|---|---|
| `StreamTextBuffer` | 合并 delta、记录已消费偏移、按帧提供新增后缀 | 浏览器调度，无 Markdown 依赖 |
| `StableMarkdownBlockDetector` | 从活动尾部提取可安全冻结的前缀 | 纯 TypeScript，可独立测试 |
| `MarkdownView` | 静态富渲染；流式模式组合稳定块与活动尾部 | 现有 Markdown / Mermaid / cite 增强 |
| `RenderUnitProjector` | 把流式块或静态消息和 segments 投影为稳定的虚拟化单元 | 现有消息判别联合、稳定块划分 |
| `VirtualWindow` | 高度缓存、可见范围、overscan、spacer、锚点修正 | `ResizeObserver`、滚动容器 |
| `ChatView` | 保持事件编排、sticky 状态和进度轨交互 | 上述 UI 单元，不承担解析算法 |

具体文件名由 implementation plan 根据现有目录确认；必须保持每个纯逻辑单元可在无 Obsidian 环境下测试。

### 5.6 滚动调度

现有 `scrollToBottom()` 会在多个事件分支中创建 rAF。实现阶段应合并同一帧的滚动请求：

- `message.delta`、工具事件和搜索结果只标记“需要滚动”。
- 同一帧最多执行一次贴底度量和一次 `scrollTop` 写入。
- `isUserNearBottom === false` 时不安排贴底写入。
- 虚拟窗口的高度校正与贴底写入必须共用调度顺序，避免一帧内互相覆盖。

右侧进度轨继续反映整个会话的阅读比例，而不是仅反映当前挂载窗口。

### 5.7 错误处理与降级

- 增量偏移与完整消息内容不一致：丢弃 UI 缓冲，从消息事实源重建一次轻量文本；不得循环重试。
- 稳定块边界不确定：不提升，继续轻量显示。
- Markdown 或增强失败：显示净化后的纯文本，记录开发日志，后续块继续工作。
- `ResizeObserver` 不可用：使用估算高度和滚动事件校正；功能可用但虚拟定位精度降低。
- 高度缓存失效：以当前可见锚点重新测量，不清空整个会话 DOM 后重建。
- 虚拟窗口发生无法恢复的投影错误：回退普通消息列表；第一、二阶段的流式性能优化仍保持生效。

## 6. 测试与验证

### 6.1 纯逻辑测试

- `StreamingMarkdownState` / `applyLightTextAction`：连续 delta、同帧合并、取消、异常结束、偏移失配恢复和 Text 节点复用。
- `splitStableMarkdownBlocks` / `StableMarkdownProjection`：段落、标题、列表、表格、引用、闭合与未闭合围栏、混合块、空内容。
- 跨块语义：Markdown 引用定义存在时不提前冻结，也不把静态文本拆成多个独立渲染单元。
- `RenderUnitProjector`：消息、工具段、compact marker、稳定块和活动尾部的 id 稳定性。
- 静态长消息投影：完整文本被拆成稳定块，逻辑消息分组、首尾 chrome 和整条复制语义不丢失。
- `virtual-window` 纯函数：可见范围、overscan、估算高度、实测高度更新、锚点修正、跳转未挂载单元。
- 滚动调度：同一帧多事件只写一次；离开底部时不自动拉回。

### 6.2 DOM 与组件测试

- 200 个 delta 不触发 200 次 `renderMarkdownToHtml`。
- 冻结块在后续 delta 后保持同一 DOM 节点。
- 流式结束后 Markdown、代码高亮、表格、引用和 Mermaid 正常。
- 选区存在时不替换相关 DOM；结束选择后完成收尾。
- 虚拟窗口只挂载目标范围；滚动前后 spacer 与总高度连续。
- 图片、Mermaid 和工具展开改变高度后，当前阅读锚点不跳。
- 右侧进度轨可跳转到未挂载消息并恢复高亮。

### 6.3 性能基准

固定场景至少包括：

1. 4K 字 / 50 delta。
2. 8K 字 / 100 delta。
3. 16K 字 / 200 delta。
4. 100 条混合消息，包含代码、表格、引用、工具段和 Mermaid 占位。

基准记录完整 Markdown 调用次数、累计脚本时间、最长主线程任务、挂载 DOM 节点数和滚动交互响应。CI 对调用次数和节点上界做确定性断言，绝对耗时由专项基准与 Sandbox 验收记录，避免共享机器波动造成假失败。

每个 plan 完成后都必须单独跑性能基准和 Sandbox 验收。不得等待第三阶段才验证第一阶段是否真正消除卡死。

## 8. 影响面

- **用户体验：** 流式文字保持连续增长；富格式可能稍后成形，但 Obsidian 响应性优先。
- **UI：** 主要影响聊天文本渲染、消息列表、滚动调度和右侧进度轨。
- **数据：** 不改消息模型和持久化格式，不需要迁移。
- **架构：** 新增 UI 内部纯逻辑单元，不改 ports、Worker 协议或构建产物，无需 ADR。
- **可访问性：** 虚拟化后必须保留消息语义、键盘滚动和按钮焦点；焦点所在单元不得被回收。
- **文档：** 属于性能与内部渲染行为，不直接改变 README 功能清单；实施完成后按 finishing 规则确认 CHANGELOG。

---

## 9. 与现有规格的关系

- `S-MSG-STREAM` 的 `Message[] + segments` 数据模型继续有效。
- `S-MD-PREVIEW` 的富块样式、复制、Mermaid、图片 overlay 和“文字持续增长”体验继续有效。
- 本 spec 明确取代 `S-MD-PREVIEW` 中“流式必须使用 rAF 全量 Markdown 重绘”以及“overlay 打开时底层必须继续全量重绘”的实现约束。overlay 仍使用打开时快照，但底层按本 spec 的轻渲染或稳定块策略继续更新。
- `S-CHAT-NAV` 的右侧进度轨交互继续有效；第三阶段将其比例与跳转改为基于完整虚拟高度和 RenderUnit 定位。
