# 点击发送后 Obsidian 白屏：诊断记录

2026 年 10 月 27 日晚，用户点击发送后整个 Obsidian 窗口白屏；重新打开后，本次输入的消息消失。本记录供维护者判断崩溃原因和后续修复范围。取证和实验于 10 月 28 日完成，未覆盖或重载日常库插件。

## 结论

旧安装包的记忆融合检索存在已独立复现的指数内存增长缺陷：每次 BM25 查询都会重新初始化英文 NLP 模型，模型依赖把已经序列化的字符串再次序列化，并写回模块共享变量。旧安装包包含该实现，崩溃前最后一个已完成阶段正是其入口之前的嵌入计算。该缺陷是本次事故的高置信原因。

消息丢失另有明确原因：聊天界面先显示用户消息并清空输入框，用户消息的持久化却在记忆准备之后。此次进程在持久化之前退出，因此重新加载时没有这条消息。

系统报告证明渲染进程发生原生崩溃，异常为 `EXC_BREAKPOINT / SIGTRAP`。报告没有完整符号及当时的堆快照，尚不能把最终原生指令与某一次字符串分配直接对应，也不能排除其他内存来源。本次没有在 Obsidian 中重现原生崩溃，不能宣称已修复。

## 已复现的增长链路

事故安装包的 manifest 为 `1.1.1`。已直接检查实际安装的 `main.js`，其记忆检索调用链与该版本源码一致：

```text
发送 → ask → 记忆主题嵌入完成
  → MemoryStore.searchIndex(query, vector, k)
  → VectraStore.hybridSearch
  → LocalIndex.queryItems(..., true)
  → setupBm25 → winkNLP(model) → model.metaCER()
```

`vectra@0.15.0` 的 `queryItems` 在 BM25 开启时每次调用 `setupBm25()`；后者每次创建 NLP 实例。`wink-eng-lite-web-model@1.8.1` 的 `dist/load-cer-meta-model.js` 包含以下赋值：

```javascript
return { machines: machines = JSON.stringify(machines), transformers };
```

第一次调用把对象变成字符串，后续调用不断转义上一轮的引号和反斜杠。模块共享变量保留了增长后的字符串，强制 GC 不能回收当前值。实际旧包中也找到相同的自赋值表达式。

小索引触发的 BM25 consolidation 异常会被旧适配器捕获，再降级为纯向量查询。但异常发生前模型加载器已改变共享变量，降级成功不会撤销增长。因此「检索还能返回结果」无法证明没有累积内存问题。

## 本地对照实验

复现脚本为 [bm25-init-growth.mjs](../../scripts/diagnostics/bm25-init-growth.mjs)。脚本使用两条合成向量，调用真实 `LocalIndex.queryItems`，模拟旧适配器的小库失败及纯向量降级。不读取 Vault、不发请求、不创建索引文件、不修改依赖文件；调用次数和内存均设有上限。

```bash
node --expose-gc --max-old-space-size=256 scripts/diagnostics/bm25-init-growth.mjs
node --expose-gc --max-old-space-size=256 scripts/diagnostics/bm25-init-growth.mjs --control
```

两组每轮都等待事件循环让出并强制 GC。对照组仅将 `metaCER()` 首次结果复用，其他查询、NLP 初始化和异常降级步骤相同。这个替换只作用于独立诊断进程，不是产品补丁。

| 组别与轮次 | 模型字符串字符数 | RSS MB | JS 堆 MB |
| --- | ---: | ---: | ---: |
| 原实现，第 1 次 | 2953 | 107 | 25 |
| 原实现，第 10 次 | 324883 | 146 | 26 |
| 原实现，第 15 次 | 10324243 | 185 | 35 |
| 原实现，第 16 次 | 20646163 | 224 | 45 |
| 对照组，第 16 次 | 2953 | 166 | 25 |
| 对照组，第 24 次 | 2953 | 184 | 25 |

RSS 是实测进程指标，会随运行环境变化；字符串长度与断言是本次复现的主要判据。对照组的 RSS 仍有增长，不能把缓存首次结果描述为「全部内存问题已解决」。另一次 18 轮探索实验中，原实现 GC 后 RSS 达到约 448 MB、JS 堆约 102 MB，随后按诊断上限停止，没有故意制造崩溃。

额外对照：相同两条合成向量走纯向量入口 1000 次，BM25 初始化次数为 0，GC 后 JS 堆从约 12 MB 保持在约 12 MB。该结果证明纯向量调用避开了已复现的模型初始化路径，不代表完整 UI 或长期运行已通过验收。

## 当前源码与消息保存缺口

当前检索实现已在 `8e82abc` 移除 `hybridSearch`，记忆检索改调 `search(vector, k)`。`src/` 中未找到开启 BM25 的调用；`src/adapters/vector-vectra.ts` 的 `queryItems` 未传入 BM25 开关。旧日常库安装包尚未包含这次变更，需走正常版本交付后再做长期验证。

消息保存缺口在当前源码中仍然存在：

- `src/ui/chat/ChatView.svelte` 的 `sendMessage()` 先把用户消息放进 UI 并清空输入，再调用 `plugin.ask()`。
- `src/main.ts` 的 `ask()` 先执行记忆检索和上下文准备，再进入 `agentLoop()`。
- `src/core/agent-loop.ts` 在 `ctx.load()` 后才调用 `ctx.addUserMessage()` 和 `await ctx.save()`。

后续修复应让已接受的用户输入在记忆准备之前完成持久化；保存失败时保留输入并显示失败，正常继续时不能重复追加。附件、取消和自动压缩路径需要一起验证。本次只做诊断，未修改上述行为。

## 验证与后续

本次定向测试为 7 个文件、55 项，全部通过，范围为聊天三阶段性能合同、渲染单元投影、虚拟窗口、记忆存储与自动嵌入门闩。这些测试没有运行完整 Svelte 界面，不能排除 UI 或第三方插件的其他问题。复现脚本原实现组、对照组均以退出码 0 完成预期断言。

建议下一步先补齐发送前落盘缺口，再验证包含纯向量记忆检索的新版本：在 Sandbox 连续执行至少 30 次记忆检索，记录空闲后的内存变化；通过后按正常发布流程交付。不要以「提高内存告警阈值」代替切断重复初始化路径。

若新版本仍出现同类增长，再在 Sandbox 收集堆快照和分阶段内存记录，追踪残余增长来源。本次没有导出用户正文、主题名称、原始日志、私有路径或密钥，也没有发布或覆盖任何插件。
