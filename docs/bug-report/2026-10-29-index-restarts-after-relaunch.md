# 1.2.0 重启后重复全量索引与进度倒退

用户反馈：升级后显示索引完成，关闭再打开 Obsidian，索引又从 0 开始，进度时高时低且会倒退。2026 年 10 月 29 日检查实际安装文件，并使用当前源码的实际方法完成隔离复现。

## 结论与影响

已确认索引任务生命周期存在缺陷：全量请求固定 10 分钟超时，超时不会停止执行中的任务；上层把超时当成索引损坏，清空目录后再次启动全量任务。旧、新任务通过同一条无任务标识的进度通道更新界面，进度因此可能倒退。

再次超时后，启动控制器返回 `null`，宿主仍把空结果按 `0` 成功、`0` 错误通知完成，界面被设置成 `ready`。两个任务晚到的完成响应已经无人接收，不能继续执行写清单和构建戳的逻辑。此时后台仍可能写向量，但下一次启动无法确认索引有效，又从全量开始。

升级后首次按新分块规则重建一次属于预期；失败被显示为完成、任务重叠以及重启后反复重做属于缺陷。

## 本机只读取证

- 实际安装的 manifest 版本为 `1.2.0`，安装包包含构建戳逻辑和 `600000` 毫秒请求超时。
- 重启后插件加载时间为北京时间 09:13:28；检查时索引目录的修改时间为 09:24:23，与启动后约 10 分钟重新建目录的路径吻合，但目录时间本身不能单独证明调用来源。
- 多次只读采样中，向量条目由 67 增至 121、130，表明确实在继续构建索引。
- 同期 `.index/ratel-manifest.json` 和 `.index/build-stamp.json` 都不存在，也没有对应 `.tmp` 文件。缺少完成记录的状态已确认，尚未从控制台取得该实例的超时错误堆栈。
- 未覆盖插件、删除索引、改写配置或重启日常库。

## 隔离复现

实验通过 TypeScript AST 提取 `src/main.ts` 中的 `smartReindex`、`doSmartReindex`，以及 `src/core/feedback-controller.ts` 中的 `notifyFullIndexComplete`，方法正文保持原样；配合真实 `WorkerManager` 和 `IndexManager` 执行。Worker、时钟和索引 IO 使用可控替身，不触碰真实索引。

输入状态为「已有向量，清单和构建戳缺失」。手动触发真实管理器登记的超时回调，测试任务挂起时的行为。

| 步骤 | 实测结果 |
| --- | --- |
| 首次启动 | 发出 1 个全量请求，超时为 600000 毫秒 |
| 首次请求超时 | 发出第 2 个全量请求；旧任务未被终止时再次清索引 |
| 交错发送进度 | 界面回调收到 `60/100 → 90/100 → 1/100` |
| 第二个请求超时 | 启动控制器返回 `null` |
| 两个旧请求随后返回成功 | 响应被忽略，写清单／构建戳回调累计执行 0 次 |
| 按当前宿主调用通知完成 | 界面字段被设置为 `index: ready, indexDocCount: 0` |

实验对上述条件作了断言，退出码为 0。复现证明代码路径存在并能产生用户描述的现象；不是在日常库中实际制造两次十分钟超时。

## 代码位置

- `src/worker/manager.ts`：固定时限到达后仅删除 pending 并 reject；没有取消后台任务。无 `_requestId` 的进度直接交给全局回调，没有与活动请求关联。
- `src/worker/inline-worker.ts`：每次请求独立异步进入 `handleMessage`，没有互斥或排队保障；前一任务挂起时仍可开始后一任务。
- `src/main.ts` 的 `smartReindex()`：对所有异常统一执行清索引和再次全量处理，没有区分「请求超时，但任务仍在运行」与「索引数据损坏」。
- `src/main.ts` 的 `writeManifestAfterFullReindex()`：依赖全量请求成功返回才执行；晚到响应被忽略后无法写完成记录。
- `src/core/index-manager.ts` 的 `onLayoutReady()`：捕获失败后返回 `null`。
- `src/main.ts` 的 `onLayoutReady()`：对 `null` 结果仍调用 `notifyFullIndexComplete(0, 0)`。
- `src/core/feedback-controller.ts` 的 `notifyFullIndexComplete()`：默认直接设置 `ready`。

## 修复边界与验收条件

需要统一修复任务调度、超时及完成语义，不能只延长固定超时：

- 同一索引只允许一个写任务运行；旧任务未停止时不得清目录或启动替代全量任务。
- 区分持续推进的长任务与无进展任务；进度及完成响应归属于明确任务，旧任务的进度不能污染当前展示。
- 超时或失败不能被通知成完成；已成功的索引元数据必须可靠落盘，只有确需重建的条件才清空有效索引。
- 测试应覆盖超过原十分钟仍持续推进、真实停滞、失败后的晚到完成、交错进度，以及成功完成后重启零重复嵌入。

本记录保留修复前的诊断事实。后续修复范围与验收见 [S-INDEX-RESTART](../superpowers/archive/S-INDEX-RESTART/specs/2026-10-29-index-restart.md)；是否完成与发布以实施计划和 Release 为准。
