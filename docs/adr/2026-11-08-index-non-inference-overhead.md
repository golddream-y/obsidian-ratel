# ADR-023 索引「非推理开销」暂不优化

- 状态:已接受
- 日期:2026-11-08
- 相关:[嵌入推理分层](../architecture/llm/embedding-inference.md)、[资产下载](../architecture/host/asset-downloads.md)

## 背景

1.5.0 把本地向量推理迁到 WebGPU 后，纯推理从 0.82 秒/块降到约 0.10 秒/块，占端到端的比重随之下降。据此形成过一个判断：**非推理开销已占端到端约 75%，是下一个主要瓶颈**，并据此排入优化计划。

这个判断只有减法依据（端到端减去推理），没有分阶段实测。在动手改存储与提交路径之前，先补了测量。

## 测量

新增基准 `tests/core/index-phase-profile.test.ts`（默认跳过，`RATEL_PROFILE=1` 打开），用真实分块器、真实分片存储、真实两阶段提交，向量用确定性伪随机填充以剔除推理成本。

200 篇 / 1000 块，本机结果：

| 环节 | 每块耗时 | 占端到端 350ms |
|---|---|---|
| 分块（线程模式，字符计数） | 0.00 ms | ~0% |
| 分块（主线程模式，token 计数） | 0.56 ms | 0.2% |
| 提交 + 落盘（8 分片） | 16.7 ms | 4.8% |
| 跨线程 IPC 往返 | 0.12 ms | 0.03% |
| 纯推理（GPU 预热实测） | 100 ms | 28.6% |
| **无法归因的等待** | **~233 ms** | **66%** |

分块与提交合计不足 5%。IPC 用 `worker_threads` 单独测得 0.12 ms/次，同样可忽略。

## 决定

**不优化分块与提交**，近期也不为「非推理开销」单独立项。理由：

1. **可优化空间已被证伪。** 分块是纯函数，提交走的是已验证的原子落盘，两者合计上限不到 5%；即使优化到零，端到端也只从 350ms 降到 333ms。
2. **真正的大头不是算法成本。** 那 66% 是推理之外的**等待**，候选来源是主线程被宿主 UI 与其他插件占用（现场出现过 `Forced reflow 14554ms`）、批次形状碎片化（每篇块数 1–215）、以及预热读数与真实负载之间的偏差。这些属于调度与宿主争用问题，不是「少写几次盘」能解决的。
3. **改提交要动可靠性地基。** 提交路径直接承载 1.4.0 的「逐篇持久化、中断可续建」承诺，任何批量合并或增量追加都会牵动恢复语义与崩溃一致性，风险与 5% 收益不匹配。
4. **场景尚未到来。** 本机 27832 块约 2 小时的索引，对个人库可接受；真正的痛点在 2.0 的大批量索引，应在那个场景下按实测重新设计，而不是现在按旧假设改。

## 后续

- 若 2.0 立项，先跑本基准并采集生产的 `索引耗时构成` 日志（分块/嵌入/提交三段），用实测占比决定改哪里。
- 若要把等待时间归因，首个动作应是量化主线程占用与批次的形状分布，而不是改存储。
- 基准随代码保留，任何人再提「非推理开销占大头」时可直接复现。

## 影响

- 「非推理开销 75%」不再作为优化的立项依据；该数字本身是减法估算，不是分阶段实测。
- 索引性能的下一步优化方向记录为：**推理调度与主线程争用**，而非写入路径。
