# Ratel 2.0 演进路线

> 2026-10-23 · 迭代计划草案 · 按本次讨论落盘；格式样本与各包设计范围仍待确认，不构成日期排期、版本或实施承诺。

本页唯一维护阶段顺序、故事范围、依赖与通过条件。产品目标与行为见[总体 PRD](../prd/2.0/README.md)及能力分册，故事完成条件见[用户故事](../prd/2.0/stories/README.md)，实时优先级与确认状态见[Project](https://github.com/users/golddream-y/projects/1)。

## 1. 当前规划范围

当前路线覆盖材料可用、知识发现、知识组织与 Skill 生态。材料可用同时包含 Ratel 的提取检索与用户的原件查看；知识组织独立考虑内置 Skill，不能成为检索前提。确定性权限、一致性与校验由工程负责，Skill 负责编排。

整体目标中的认识澄清、确认沉淀、知识效力、阶段上下文、成果生产接续和结论演进尚未形成当前交付批次，后续需先细化需求。用户方法提炼和独立任务接续不纳入本轮迭代计划。此前「1B 任务可续」及按「先沉淀、再更新」安排阶段的建议不再作为当前路线依据。

## 2. 交付包与迭代顺序

按完整用户结果拆交付包，按技术依赖安排顺序。材料与搜索为主线，Skill 支撑可并行，知识组织先用已有笔记能力验证，再扩展到混合材料。26 个故事保留验收身份，不对应 26 份 spec；以下包和阶段也不对应版本号或等长工期。本节取代此前 I1～I5 的候选批次。

### 交付包与故事映射

| 包 | 用户结果 | 故事范围 | 必须一起成立的条件 |
|---|---|---|---|
| A · PDF 完整可用 | 选定范围内的笔记和文本 PDF 能读、能搜，能回原件核查 | US-2-001、002、004～008 在首批范围内联合验收 | 提取与页位置、原词查找、语义索引接入、原件查看、变化失效、范围收回、基础处理控制；按实际能力渐进可用 |
| B · PPTX 接入 | 找到幻灯片文字及出处，并查看原件、了解盲区 | US-2-003；复验 US-2-001、004～008 | 保留幻灯片顺序与定位，明确备注、图片、图表覆盖；复用 A 的接入、搜索与变化处理机制 |
| C · Excel 与 Word 接入 | 表格数字带有表头、单位和位置，Word 正文可查可核查 | Excel：US-2-009；Word：US-2-010；各自复验共用故事 | 两种格式分别验收；保留表格必要语义，说明公式与缓存值边界，Word 不承诺稳定页码 |
| D · 大库与搜索增强 | 大量材料逐步可用，检索质量与编辑响应满足约定样本要求 | US-2-011；复验 US-2-004、005、007、008；搜索底座增强共同验收 | 扩展规模调度、资源控制与增量效率；依据实测改善召回和上下文，补齐链检索与反向追踪的实际缺口 |
| E1 · 已有 Skill 可靠可用 | 描述任务后找到合适的已安装 Skill，并按需读取正文和资源 | US-2-017、021；复验 US-2-025 的基本停用 | 中文发现、大量 Skill 下的可发现性、长正文与参考资源读取、停用生效；为内置预览与组织 Skill 提供支撑 |
| E2 · 第三方 Skill 引入与维护 | 缺能力时获得可核查推荐，安装后完成实际任务，后续可维护 | US-2-018～022 联合验收；随后增强 US-2-023～026 | 先选任务、样本和依赖；来源记录、基本停用、首次安装失败保护随安装交付，更新比较、保留定制和更新恢复随后交付 |
| F · 局部知识组织 | 理解局部组织问题，选择调整并建立、维护真实入口 | US-2-012～016 | 012、013、015 联合验收诊断、建议与执行；014 建入口与 016 刷新可独立使用；保留人工编辑，不默认搬迁全库 |

共用故事随每种格式重新验收。在 A 中验证通过不代表 PPTX、Excel、Word 自动通过；跨包故事按实际覆盖记录部分完成，不能提前标记整体完成。D 集中扩大规模和改善质量，基础质量验收、恢复和权限不推迟到 D。

| 第三阶段 | C：建议 Excel 优先，随后 Word，各自交付 | E2：选定真实场景，贯通推荐、安装与任务使用 | 数值及必要结构可核查，文档内容可用；第三方 Skill 从候选到实际任务结果有完整证据 |

### 首轮设计范围与共同门槛

近期先细化 A 与 E1。A 在一种格式中验证原件、派生内容、位置和状态之间的边界，再用 B、C 检验复用；不先建设脱离用户场景的通用材料平台。内置预览环境准备复用已有插件工具，不等待 E2 的在线 Skill 安装链路。

| 时点 | 需要确认或验证的内容 |
|---|---|
| 进入 A 设计前 | 文本 PDF 与笔记的代表样本、页位置与提取覆盖、查看和降级方式、单文件体积门槛及超限行为；128 MiB 仅为待实测候选 |
| 进入 E1 设计前 | 已有发现与资源读取的实际缺口、中文任务和长正文/资源样本、停用对会话的实际效果 |
| 各包设计前 | 对应分册与故事的明确范围、预期结果和验收样本；范围确认后才拆 spec/plan |
| 从 A 开始持续验证 | 原词查找、语义召回、上下文和来源质量；基础暂停、取消、优先处理、单文件失败隔离和重启恢复；权限与排除变化 |
| 各格式交付时 | 正常、部分覆盖、失败、变化、删除、范围收回及缓存处理；已就绪能力先用，旧内容不得冒充当前内容 |
| E2 任务选择后 | 工具、脚本、资源与运行环境依赖；兼容检查、安装与真实任务联合验收，未知依赖不标为兼容 |
| D 集中验证时 | 扩大文件数、单文件和总量样本，测吞吐、峰值资源与编辑响应；基于瓶颈优化，不重复处理未变内容 |

链检索与反向追踪只作为搜索底座增强：既有行为先回归，新增缺口按真实链接、引用方向和原文位置验收。搜索底座与 Agent 使用结果分别检查，评价方法见[检索分册](../prd/2.0/capabilities/knowledge-discovery.md)。从 A 起记录质量与性能基线，具体规模、召回和延迟门槛实测后确认；一次强模型成功不能代表全部配置。


## 3. 版本与分支边界

| 情况 | 管理原则 | 尚未确定的内容 |
|---|---|---|
| 阶段与发布 | 一个阶段可分多次发布，一次发布可包含多个阶段的独立能力 | 阶段不自动映射版本号或日期 |
| 兼容的独立增强 | 建议从 develop 经短期功能分支集成，按批准范围发布 | 是否进入某个 1.x 版本 |
| 新交互或数据机制 | 试用能力明确启用，说明兼容与回退，验证后决定默认启用 | 试用方式、迁移和默认开启时间 |
| 不兼容的数据迁移 | 单独决定下一代集成线与迁移安排 | 不先建立长期巨大 2.0 分支；开关不能替代迁移设计 |
| 2.0.0 门槛 | 按完整用户价值与实际验证选择发布范围 | 按能力归属和代表场景验证后再选择，不沿用此前阶段门槛 |
| 既有能力提前增强 | Skill、生态配置等独立改进可先交付 | 可选能力需有运行兼容性和代表任务证据 |

### 阶段固化与增量演进

每个阶段验收后，把该阶段已确认的范围、契约与验证结果固定下来；后续阶段只做增量扩展或明确的迁移，不推翻重来。

| 要求 | 执行含义 |
|---|---|
| 契约先于实现 | 进入阶段前确认本阶段要固定的边界（如派生内容与索引记录的关系、状态语义、位置表达方式），避免下一阶段改结构 |
| 交付即可继续 | 阶段验收后的能力可被后续阶段直接复用；新增格式或抬高规模档位不要求重做已交付部分 |
| 变更走迁移 | 确需改动已固化契约时，单独设计迁移与兼容策略，并说明对既有索引、缓存与已生成成果的影响 |
| 验收留证据 | 每阶段的代表样本、覆盖范围与失败路径有记录，供后续阶段回归 |

规模档位、格式清单与队列容量按阶段实测决定，不在阶段开始前一次定死。

### 2.0 功能稳定后的组件独立化评估

2026-10-20 确认：自有底层组件拆包、独立维护和独立发包，放在 **2.0 功能稳定之后**再评估。当前优先交付用户能力，保持插件内部模块边界，并复用合适的开源组件。关联跟踪项：`REQ-POST2-ENG-001`。

| 项目 | 已确认的安排 |
|---|---|
| 启动时机 | 2.0 功能稳定后再启动评估；具体日期和版本未定 |
| 当前边界 | 独立拆包与发包不作为 2.0 的交付目标或发布门槛；现成开源库和可选本地服务仍可继续验证 |
| 当前工程原则 | 处理逻辑、界面与 Obsidian 适配保持清晰边界，不提前建设通用框架 |
| 后续评估依据 | 先验证现成方案的实际缺口，再判断需求共性、真实复用场景及长期维护成本 |
| 待决定事项 | 是否拆包、抽取范围、同仓或独立仓库、维护与发布方式，均在评估后决定；不预先承诺自建通用知识引擎 |
