# 自适应索引与低打扰运行

关联需求：`BUG-1-INDEX-PERF-001`，在 [Project](https://github.com/users/golddream-y/projects/1) 草稿跟踪，未创建公开 Issue。2026-11-02 用户要求先做相关架构设计，技术细节沿用 Agent 自审裁定；本轮不启动实现或发布。

## 下一次交付目标

**索引期间 Obsidian 能正常使用。** 输入、滚动、切换笔记和查询不被索引阻塞；正确性不回退（不丢完成记录、不误用旧数据、不重复索引）；构建耗时、内存与磁盘写入量在可接受范围。三项分别验收，界面变流畅不能替代其余两项。

本次一并收敛 1.3.0 的可靠性遗留（派生清单恢复、配置切换语义、写入一致性等）：先用复现测试固定，再把同一套索引内核迁入独立线程。调速与速度模式后置，等线程隔离与可靠性收口完成后再完善。

## 使用目标

用户进一步明确：卡顿发生在 Obsidian 客户端，不能仅按整机资源不足处理。首要目标是索引期间输入、滚动和切换笔记保持响应，因此先隔离界面线程上的重计算与存储，再以自适应调度控制后台开销。

索引在电脑负载较高、用户操作 Obsidian 或检索等待时主动降速；环境恢复后缓慢提速。用户无需根据电脑型号手工选择批次参数，已完成的逐篇索引在暂停、退出和重启后继续复用。

「自适应」描述根据可观测信号调节工作节奏，不承诺读取整机 CPU、温度、剩余物理内存或把进程 CPU 严格限制在某个百分比。无法获得压力信息时采用保守策略，不把信息缺失视为电脑空闲。

## 范围与验收

| 场景 | 预期行为 |
| --- | --- |
| 空闲且响应稳定 | 逐档加速，有批次和连续运行上限 |
| 输入、切换笔记、交互检索等待 | 降速或暂缓启动下一批索引，已在执行的存储提交安全收尾 |
| 批次较慢或界面响应变差 | 减少后续批次规模并增加休息，不只在文件间休息 |
| 压力信息不可用或窗口长期隐藏 | 保守运行，不据此判断空闲或激进加速 |
| 用户主动暂停 | 完全停止新索引调度，自动调速不得擅自恢复 |
| 关闭、恢复、取消 | 保留逐文件完成记录与事务恢复语义，调速不改变内容/配置指纹 |
| 大 JSON 提交造成卡顿 | 独立识别存储阻塞；不能用平均占用下降宣称界面阻塞已解决 |

本设计建议默认「自适应」，保留「低占用」「全速」手动覆盖。全速仍遵守单写入者、交互仲裁、内存与批次安全上限，不通过关闭校验或耐久提交提速。

不新增遥测、远端服务、自动切换 API 模型或更改索引模型/分块配置。总体机制见[索引执行与存储架构提案](../architecture/proposals/2026-11-02-index-runtime.md)；本次变更范围与验收见 [S-ADAPTIVE-INDEX](../superpowers/specs/2026-11-02-adaptive-indexing.md)。先收口架构与可行性，再拆实施 plan。
