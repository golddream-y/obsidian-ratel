# 问题与场景

本页梳理需求的起点，不指定解决方案。已知场景是用户把笔记与 Excel、PPT 等工作材料集中放入 Obsidian；以下问题还需要结合代表性任务判断频率和影响，不能全部当成已经发生的故障。

## 五类问题

| 类别 | 典型表现 | 对工作的影响 |
|---|---|---|
| 内容理解与检索 | 文件存在但正文不可搜索；图片、表格、公式或备注没有被正确理解 | 材料不可用，或提取了文字却丢失原意 |
| 来源与知识关联 | 找到结论却无法回到页、段落或单元格；依据散落在多个文件 | 核查成本高，难以还原判断依据 |
| 版本与文件治理 | 多个最终版并存，内容更新后仍引用旧结论；移动或删除破坏引用 | 过期材料被误用，变更影响不清楚 |
| 规模与运行体验 | 首次处理耗时，频繁修改反复处理，空间和内存增长 | 日常编辑受影响，用户不敢把更多材料放进来 |
| 安全与结果可信度 | 不知道读了哪些内容、发到哪里、漏掉哪些文件；未找到被当成不存在 | 用户不能控制或判断答案是否可信 |

这些问题覆盖材料层，还要检查知识处理过程中的断点：有材料不等于有结论，有结论不等于已确认，已确认也不等于适用于所有任务。

## 三个贯穿场景

### 项目材料参与新任务

用户准备项目汇报，工作区里已有会议记录、预算表和旧方案。首先要知道哪些材料与本次目标相关、采用哪个版本、哪些关键问题还没有依据。AI 给出带来源的材料组合与解释，用户能回到原件核查。

需要验证的重点是找到正确证据和暴露覆盖盲区，而非只生成一份看起来完整的总结。若接着生产汇报，新成果还应能说明引用了哪些依据，以及新增了哪些判断。

### 隐性判断变成可复用知识

用户和 AI 讨论一个方案，已有经验、直觉、外部资料和临时猜测交织。通过澄清和比较，形成“采用什么、为什么、何时适用、什么尚未确定”。确认过的结论供后续任务复用，不把临时话题或被否定方案当成当前决定。

需要验证的重点是保留关键判断并减少重复解释，同时避免把每轮聊天都变成需要维护的正式文档。

### 新证据触发知识修订

预算表更新，或一次实践否定了原来的做法。用户希望知道哪些结论、方案和成果可能受影响，选择修订有效内容，并保留旧结论及改变理由。

需要验证的重点是新旧内容的可辨认性、影响提示是否可信，以及修订能否改善下一次使用。发现“可能受影响”不等于已经证明所有下游依赖，不能自动批量重写。

## 确定优先级前要补的证据

从真实任务收集：最常发生的断点、一次发生的返工量、错误后果、现有做法，以及用户愿意承担的配置与确认成本。选择第一条工作链路时，用这些证据比较需求；不要因为某个解析工具容易接入，就把格式支持自动排在第一位。
