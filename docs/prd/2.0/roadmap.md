# 阶段与版本决策

本页记录需求收敛和版本选择原则，不给未经确认的日期、版本容量或分支承诺。2.0 的发布边界是形成一段完整、可验证的新工作体验，不是把全部长期愿景做完。

## 当前已确定与未确定

已确定产品目标与知识处理主线；已授权编写需求草案并用 Project 维护进度。需求文档尚未确认，优先级与首期范围未确定，也没有新的实施分支、发布 Milestone 或执行计划。

下一步先对比真实任务的频率、错误后果、返工量、可验证性和配置负担，再选择第一条交付链路。文档审阅不自动批准技术候选，需求确认也不直接构成实施授权。

## 首期闭环的三个候选

| 候选 | 贯穿的工作过程 | 优先验证什么 |
|---|---|---|
| 项目材料成为可核查依据 | 材料接入 → 任务检索 → 来源核查 | 覆盖、版本和定位是否可靠，是否减少查找与确认成本 |
| 讨论结论被下一次任务复用 | 澄清与比较 → 确认结论 → 后续任务使用 | 是否减少重复解释，是否区分假设与有效决定 |
| 实践反馈修订已有知识 | 新证据 → 影响提示 → 确认修订 → 再次使用 | 是否避免使用旧结论，影响范围和提示是否可信 |

三个候选用于比较，不代表三个版本或三个分支。办公材料工作区可成为其中一个验证场景，不预先认定必须先完成所有格式解析，才能开始知识沉淀与消费。

## 版本与分支选择条件

可独立使用、兼容现有工作方式且验证充分的改进，可以讨论进入后续 1.x；需要一起成立的知识流程、明显改变交互或涉及迁移的能力，考虑先放进下一代试用范围。是否符合这些条件需对具体需求判断，不能仅靠开关隐藏就认为没有兼容风险。

稳定维护线负责哪些修复和功能、下一代集成线是否需要建立、功能分支从何处创建与合入、预览如何试用以及正式发布如何切换，都要在首期范围确认后作出决策。本稿不预设 develop 面向哪个版本，也不创建一个长期巨大 2.0 分支承载所有探索。

## 进入设计之前的确认清单

- 首要用户任务、当前断点和第一条可验证的工作链路。
- 首期纳入的需求、明确不包含的能力，以及用户应得到的结果。
- 代表性材料、人工核查依据和质量/资源验收口径。
- 1.x 与下一代试用的交付边界、必要迁移和回退要求。
- 需求负责人、发布范围及对应的分支和集成原则。

这些内容确认后再拆 spec；设计验证可能要求回到需求调整时，记录原因并重新确认受影响范围。具体工程任务、选型、文件接口和依赖顺序放到后续设计，不在需求阶段提前固化。
