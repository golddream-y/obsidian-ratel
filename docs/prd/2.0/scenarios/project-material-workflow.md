# 场景示例：项目材料参与一次真实任务

> 2026-10-20 · 场景示例 v0.2 · 用于检验需求连贯性，不定义首期范围；产品行为以总体 PRD 和能力分册为准。

本例贯穿整体目标，包含尚未进入当前故事的生产、确认沉淀和结论复用。场景出现某个环节，不代表它已纳入当前交付范围。

用户把项目笔记、预算表、旧方案和参考文档放在 Obsidian，希望用这些积累准备一次汇报，并让这次工作留下的判断供下次使用。本例展示完整工作过程可能需要的体验，不要求用户先整理好整个库。

关联需求：[KS：沉淀](../requirements.md#req-2-ks-001)、[KC：消费](../requirements.md#req-2-kc-001)、[KP：生产](../requirements.md#req-2-kp-001)、[KE：演进](../requirements.md#req-2-ke-001)、[WS：工作区](../requirements.md#req-2-ws-001)。对应条目位于 [GitHub Project](https://github.com/users/golddream-y/projects/1)；尚无正式 Issue，本文不新建需求 ID，也不构成实施授权。

## 场景与完成条件

代表任务是：“用这个项目的材料，准备给负责人看的阶段汇报，说明进展、预算和需要决策的问题。”这是用于讨论的示例，后续以脱敏或虚构样本验证，不读取私人工作材料做默认验收。

输入可能包含会议笔记、Excel 预算、PPT 旧方案、Word 说明和 PDF 参考资料。交付实际支持哪些格式、版本与内容类型需要确认；“格式支持”必须说明是否包含图片、图表、备注、公式和扫描页。

本例以可继续编辑的 Markdown 汇报稿作为成果候选：关键事实能核查，新增建议与引用事实可辨认，缺失依据有说明。用户可以选择沉淀关键决定，之后用新任务验证这些决定是否被正确复用。

```mermaid
flowchart LR
    A[明确汇报目标与材料范围] --> B[检查可用内容与盲区]
    B --> C[查找依据并核查来源]
    C --> D[形成和修订汇报稿]
    D --> E[选择并确认可复用结论]
    E --> F[下次任务复用并检查变化]
    F --> C
```

流程允许跳过无必要的步骤：用户只想查资料时不强制生成成果；只要草稿时不强制沉淀；有效的既有授权可沿用，不重复逐步询问。需要改变任务范围、关键结论或授权边界时再由用户决定。

## 用户过程与产品反馈

### 1. 明确目标和材料范围

用户提供任务目的、面向对象以及材料目录或选定文件。Ratel 根据缺失信息澄清会影响成果的事项，例如汇报时间范围和预算口径；能从材料确定的背景无需反复询问。

开始使用前，用户能理解此次包含哪些材料、排除了什么、是否需要模型或外部工具接收内容。后续发现必须读取其他材料时解释原因；对超出当前授权的部分先取得许可。范围内的文件内容不能自行扩大权限。

本步形成一份简短的任务约定：目标、材料范围、预期交付和待确认问题。它服务当前任务，不要求用户填写固定表单。

### 2. 让材料变得可用

文件留在原有工作位置，原件保持独立；供检索和阅读的派生内容可重建，不应把它伪装成新的权威原件。是否需要安装预览或编辑插件单独说明，不能为读取材料默认安装一组插件。

用户能检查哪些文件尚未处理、正在处理、可用、只覆盖部分内容、失败或不支持；失败有原因和可行的下一步。支持暂停、取消和有针对性的重试，具体操作形态后续设计。未完成的部分不能计入已覆盖范围。

对于几十兆文件和大批量材料，优先让已可用部分参与任务，并说明盲区。处理时日常笔记编辑应保持可用，用户可控制任务；不按文件大小直接推断内容量或承诺质量、耗时与费用。

### 3. 查找依据并核查来源

Ratel 按任务问题查找材料，支持原词线索和语义相关内容，并沿现有引用、反向链接继续追踪；推测的关系要明确区分。用户可查看答案依据、原材料身份、采用的版本和实际定位信息。

定位能力按内容区分：笔记可回到标题或段落；PPT/PDF 优先定位页；Excel 优先说明工作表、区域以及解释数值所需的表头和单位。以上是候选目标，不代表每种格式均能精确跳转；无法跳转时提供可核查位置，不得展示无效的“精确引用”。Word 的定位需要结合标题或段落讨论，不能承诺稳定页码。

遇到同名文件、旧方案与新会议记录冲突时，展示差异和来源，不根据文件名或修改时间擅自裁定当前决定。搜索无结果时说明搜索范围和未覆盖内容。表格中的数值需要原始依据和必要计算核查，不能把模型的口算当作工具验证。

本步产出支持汇报的依据、待确认矛盾和缺失信息。用户可以继续补材料，也可以接受有明确缺口的草稿。

### 4. 形成与修订成果

Ratel 先根据任务需要给出结构和待解决问题，再逐步组织内容；用户明确要直接成稿时可沿用已有目标生成草稿。重要的是能够在结构、事实或口径层面修订，而不是强制每次确认提纲。

引用事实应保留可追溯依据；AI 新提出的建议、用户作出的选择及尚未核实的说法能够辨认。用户修订一个关键口径后，后续相关段落使用修订结果，暴露尚未完成复核的部分，不宣称所有下游内容已经自动校正。

保存或修改文件沿用实际权限，现有人工成果不得被静默覆盖。中断后能说明已保存版本与未完成部分；恢复时核对材料及目标变化，避免把旧进度误当作当前完成状态。

### 5. 确认值得沉淀的判断

用户可以说“把这次决定留下”，或在结束时选择是否查看候选。Ratel 提炼少量值得复用的结论、理由、适用条件、依据和未决问题，用户可修改、逐条确认、拒绝或跳过；不要求保存整段聊天。

例如：“采用分阶段投入，原因是预算上限尚未确认；预算批准后重审。”这里既有决定，也有条件和未决问题，不能只留下“采用分阶段投入”并当作永久规则。

确认结果留在用户可查看和修改的位置，位置与呈现形式待设计。确认知识不赋予其中内容新的操作权限；被拒绝或尚待确认的候选不能在后续任务中冒充已确认决定。

### 6. 下一次复用并处理变化

用户再次准备同项目汇报时，Ratel 在允许范围内查找相关决定，结合当前任务与适用条件使用，减少重新解释。其他项目的结论不能因为相似就自动变成当前约束。

原件发生变化时，先区分内容是否已重新处理、引用是否仍可定位、已知结论是否需要复核。材料更新不直接推翻结论。在结论演进被纳入交付范围后，可针对已记录的来源关系提示“可能受影响”，用户选择保留、修订或替代，并留下理由；无法确认的影响不得说成已证明的依赖。

原件移走、删除或权限收回后，不再把旧摘录当成当前可访问原件。历史依据如何保留、排除后是否清除派生副本与已生成成果，属于必须明确的边界；无法撤回的外发或已有成果要如实说明，不能承诺撤回权限即可抹去历史。

## 异常与继续方式

| 用户遇到的情况 | 必须说明的事实 | 可选的继续方式 |
|---|---|---|
| PPT 主要是图片，或 PDF 是扫描件 | 文字覆盖不足，视觉内容尚未处理 | 补充可读材料，或明确启用另行授权的识别能力 |
| 工作表可读取，但公式或图表含义未验证 | 已取得什么值、哪些关系无法确认 | 查看原表并核查；缺少必要依据时不输出确定结论 |
| 文件正在被外部软件改写或暂时锁定 | 当前内容可能不完整或无法读取 | 稍后重试，保留上次结果的历史身份 |
| 原件改了，旧派生内容尚未更新 | 已知变化与当前覆盖状态 | 等待刷新，或明确用旧版本作历史参考 |
| 检索命中但引用位置失效 | 能否确认同一版本、能否重新定位 | 重新定位、换依据或撤掉精确引用 |
| 工具不可用、任务取消或模型中断 | 已完成操作与未完成部分 | 使用已保存成果、补充工具或从可验证位置继续 |
| 某个来源被排除或不允许外发 | 此次不可使用的内容及历史结果限制 | 重新选择依据，停止依赖该来源的后续处理 |

## 场景与当前需求的对应

| 场景环节 | 需求位置 | 当前覆盖 |
|---|---|---|
| 材料处理与查看 | 材料分册 | 有候选故事，格式与样本待确认 |
| 检索与来源核查 | 检索分册 | 有候选故事；链检索等需按实际能力核对 |
| 组织入口 | 组织分册 | 可按需使用，不是开展任务的前提 |
| 准备工具与方法 | Skill 分册 | 有候选故事，不能把安装成功当成任务完成 |
| 汇报生产、确认结论与后续复用 | 总体 PRD 的 KP、KS、KE | 尚未细化为当前路线中的交付故事 |

本例不独立维护首期清单。具体交付范围以确认后的故事与演进路线为准；完整场景样例可以长期保留，用于发现能力之间的断点。

## 候选验收与样本

建议使用带人工核查依据的虚构项目：新旧会议记录、一份含表头和单位的预算表、一份带页序的旧方案、一份参考文档，并加入扫描页、不可读材料和跨项目相似结论。格式、数量、大小及内容类型在进入 spec 前锁定；下表尚未执行。

| 核查项 | 候选通过条件 |
|---|---|
| 范围与覆盖 | 能列明实际使用、排除和未覆盖材料；未处理或失败文件不会被当作搜索已覆盖 |
| 依据与定位 | 样本中的关键事实可回到正确原件及可核查位置，引用能支撑对应说法；无法精确定位时明确降级 |
| 版本与冲突 | 预设的新旧差异、冲突与缺失可辨认，不以“最新文件”自动取代用户确认的判断 |
| 成果与修订 | 汇报符合明确的目的、时间和口径；修订关键口径后，已知相关内容重新检查或列出未检查部分 |
| 沉淀与复用 | 只把用户确认的结论当作已确认；后续任务不把被拒绝或不适用的结论当作当前决定 |
| 变化与恢复 | 来源变化、引用失效或中断后，结果的有效范围清楚，能按实际能力继续；不静默宣称完成 |
| 安全与成本 | 被排除内容不参与新的读取和外发；能说明处理位置与可获得的用量，未知费用不显示为零 |

质量样本应在确认的模型配置下核查，并比较轻量与较强模型的表现；不能用单次成功代表所有模型可用。另记录相同任务的人工查找次数、关键核查耗时、编辑响应、确认次数、处理进度及资源消耗。容量、延迟和质量门槛需要样本基线，当前不填未经测量的数字。

## 示例使用边界

格式、定位降级、Markdown 成果及结论复用均为样例选择，不替代交付决策。待确认事项由 Project 跟踪，确认后的产品要求写回对应分册，交付顺序只在演进路线维护。技术 spec 在对应需求文档确认后再编写。
